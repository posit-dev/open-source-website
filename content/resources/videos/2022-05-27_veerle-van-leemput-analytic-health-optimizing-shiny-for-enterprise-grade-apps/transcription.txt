<h3>Smart coding and cache</h3>

<p><a data-t="2263">So that's one thing that you can optimize.</a> <a data-t="2268">But most of the game really is to be made in the app itself.</a> <a data-t="2268">So how are you going to make your app fast?</a> <a data-t="2274">How are you going to make your app enjoyable?</a> <a data-t="2280">Because that is part of building enterprise-grade apps.</a> <a data-t="2280">They need to work great.</a> <a data-t="2285">People expect a lot from them.</a> <a data-t="2285">So smart coding.</a> <a data-t="2285">How are we going to speed up our Shiny application?</a> <a data-t="2293">One way we can do that is by using cache.</a> <a data-t="2293">And cache is an interesting way of kind of reducing the time it takes to get output.</a></p>

<p><a data-t="2299">So imagine that people can hit a button in your Shiny app.</a> <a data-t="2307">And once they hit that button, there will be a very lengthy calculation running.</a> <a data-t="2311">I don't know.</a> <a data-t="2311">Maybe you have some kind of machine learning model or something.</a> <a data-t="2316">But they choose one input.</a> <a data-t="2316">And the calculation runs and it gets an output.</a> <a data-t="2322">It's obviously a shame if then a second user comes in, chooses the exact same input, does the calculation again, and gets the exact</a> <a data-t="2333">same output again.</a> <a data-t="2333">It's kind of a waste of time.</a> <a data-t="2333">Why should you do that calculation twice?</a> <a data-t="2337">So this is where cache comes in.</a> <a data-t="2337">Because what you also can do is say, okay, well, the first user requested a result for this input.</a> <a data-t="2342">Input A, we call it.</a> <a data-t="2342">We do that lengthy calculation.</a> <a data-t="2351">Yes, it takes some time.</a> <a data-t="2351">But for the next ones, the next users, we're not going to do that.</a> <a data-t="2355">No.</a> <a data-t="2355">Instead, we're going to immediately use the results that were being cached from that calculation.</a> <a data-t="2360">So cache is basically a way of storing your output somewhere, in this case, on your server or wherever you choose to store it.</a> <a data-t="2367">And then retrieving it from storage instead of doing the calculation.</a> <a data-t="2373">So especially if you have a large audience for your app, it can save a lot of time.</a> <a data-t="2378">And especially if a large audience is doing many of the same things.</a> <a data-t="2384">And not only if you have a large audience, even if you have just one user using your app, but it's constantly switching between input A, B, C, A, B, C, B again, C again.</a> <a data-t="2399">It's kind of requesting constantly that same calculation because he's just shifting inputs</a> <a data-t="2404">and he forgets kind of what the outcome of A was, so goes back again.</a> <a data-t="2404">So even for single users, it can <p><a data-t="2411">There are two ways you can implement cache in Shiny.</a> <a data-t="2417">The first is the memoirs package, which kind of helps you to store functions and the result of those functions as cache.</a> <a data-t="2425">And you have Shiny's bind cache function.</a> <a data-t="2431">I have an example of both of them on my GitHub page, and I will share that afterwards.</a></p>

<h3>Background processes with <a href="/software/callr/">callr</a></h3>

<p><a data-t="2510">Another smart thing you can do is using background processes, and I touched upon it a bit by saying that if you have multiple users per connection, that they have to wait for each other because</a> <a data-t="2523">the session is occupied.</a> <a data-t="2523">Well, that sometimes can happen, and we don't want that, because we don't want to have parallel execution.</a> <a data-t="2530">No, we want to have asynchronous execution of code, especially if you're developing an app for multiple users.</a> <a data-t="2536">You want them to be able to do things at the same time and not be affected.</a> <a data-t="2540">And in fact, you also don't want a user to have to wait while something is being calculated and that he or she cannot do anything in the app.</a> <a data-t="2550">So let's say a user hits a button to kind of render a graph, and then in the background, some data is being retrieved from the</a> <a data-t="2562">database, and then calculations are being done, and then the graph is being rendered.</a> <a data-t="2562">Well, maybe the user doesn't want to wait those, I don't know, 30 seconds for the graph to show up, but maybe in</a> <a data-t="2573">between, the user wants to look at another table and maybe hit another button for a lighter</a> <a data-t="2578">calculation or another calculation.</a> <a data-t="2578">You don't want people to wait.</a></p>
