<h3>The Mythical Man-Month and software complexity</h3>

<p><a data-t="216">So if you've never heard about Fred Brooks, he was at IBM and led one of the largest software projects of the 20th century, building OS360, IBM mainframes.</a> <a data-t="234">This led him to write the Mythical Man-Month in 1975, which you say, wow, 1975 is a long time ago, 51 years.</a> <a data-t="238">Still is enduringly one of the most cited and most influential works on software management and software engineering in history.</a> <a data-t="248">And even today you're starting to see, you know, I wrote an essay about the Mythical Man-Month, like Martin Fowler just wrote an essay about it.</a> <a data-t="257">It is still influencing minds and it is coming up more and more in today's context of agents carrying an increasingly large burden of the software that we're writing.</a></p>

<p><a data-t="268">He wrote a follow-up essay to the Mythical Man-Month that was also very influential called No Silver Bullet, which introduces, I think, a helpful framework in thinking about software complexity that I will come back to and explain.</a></p>

<p><a data-t="282">Brooks's Law, the idea that adding manpower to a late software project makes it later, it makes it later.</a> <a data-t="292">It's one of those things that, you know, people forget and then they have to relearn the hard way.</a> <a data-t="297">I don't know if any of you have been in a company where a pointy haired boss says, this project is behind, we need to hire engineers to make it go faster.</a> <a data-t="307">I'm usually the person in the room who's saying, wait, wait, like, have you read the Mythical Man-Month?</a> <a data-t="314">Like, are you sure that this is a good idea?</a> <a data-t="316">Maybe the problem is actually that you have the wrong people working on the project, not that you need to add people.</a></p>

<p><a data-t="327">And so this idea of the surgical team that a small team of elite people outperform large teams of average ones is also one of the reasons why startups can deliver innovations and disrupt industries in, you know, short amounts of time and run circles around their much larger and more well-equipped competitors.</a> <a data-t="353">One of the reasons that adding people to a software project can make it go slower is because of the communication overhead, which grows quadratically with the number of people.</a> <a data-t="362">And so, you know, a 20 person software, 20 person engineering team versus a five person engineering team, there's just a lot more overhead in, you know, delegating work, splitting up tasks, going through design, getting everybody on the same page.</a> <a data-t="388">You need to introduce layers of management to keep people on track.</a></p>

<p><a data-t="396">Another idea that comes from this book is the idea that the difference between a working software, you know, project and a software product that you can sell and can be maintained in production is roughly like an order of magnitude in the amount of work.</a> <a data-t="435">And, you know, now when we have agents producing software and it's alluringly simple to sit down with Claude Code, build a brand new piece of software and say, oh, looks good, I tested it, it works, like, let's ship it.</a> <a data-t="448">And it's kind of missing kind of that layer of work, which is described in this 9X gap that would be involved in, you know, actually running that project in production over a long period of time and all the problems that can come up along the way.</a></p>

<p><a data-t="467">And so, you know, so a lot of these ideas are summed up in thinking about software architecture and software design is this notion of conceptual integrity.</a> <a data-t="477">And so it's the idea that when you look at a software project, you want it to seem like it was designed by one mind.</a> <a data-t="483">So like one kind of coherent set of ideas, even if there were many people implementing and developing it.</a> <a data-t="488">And so if you have a project that has a bunch of disparate or like discordant ideas, then, you know, that can create a lot of problems as the project scales.</a> <a data-t="502">And so Brooks says, you know, if the project reflects one set of design ideas, it's better than having many good but independent and uncoordinated ideas.</a> <a data-t="512">And of course, nowadays we have agents jumping in and adding lots of independent and uncoordinated ideas to all of our software projects.</a></p>

<h3>Essential vs. accidental complexity</h3>

<p><a data-t="522">So in the No Silver Bullet essay in 1986, Brooks introduced this idea of two kinds of software complexity, the essential complexity, which is basically what the system solves, how it needs to be designed in order to be a working solution for what you're trying to build.</a> <a data-t="555">And that involves the conceptual integrity and having a coherent picture of like these are the essential set of features for this to be a complete system.</a> <a data-t="566">If we take anything out, the project is no longer a solution for what we're trying to solve.</a> <a data-t="573">And then accidental complexity is everything else that is introduced by our tools and processes and technologies that we're using to build the system.</a> <a data-t="583">And so that involves our programming languages, our build tools, like all of our systems that do testing and QA and continuous integration, you know, the boilerplate that's involved with interacting with databases and all that fun stuff.</a></p>

<p><a data-t="609">And so agents are tremendously powerful tools for dealing with all of this accidental complexity that comes up while you're building a software project.</a> <a data-t="621">You can say, you know, hey, Claude, hey, Codex, you know, hey, Gemini sometimes, go and refactor, you know, all of this code, change the test framework, rewrite all of the tests.</a> <a data-t="635">It's happy to dive in and attack and deal with all of this complexity that is introduced by, you know, the tools and systems that you're using to build the project.</a></p>

<p><a data-t="652">And I'm encountering this firsthand myself as I've largely moved on to use other programming languages other than Python, which I will show you in more graphic detail in a little while.</a> <a data-t="662">I've never written a line of Go professionally or a line of Swift professionally.</a> <a data-t="667">And yet I'm, you know, in any given day, I might be slinging, you know, 5 or 10 or 20,000 lines of code in these programming languages I'm not an expert in.</a> <a data-t="610">Like, what are the right tools and frameworks and libraries that I should be using in each language.</a> <a data-t="616">But, you know, I do look at the code and see whether, like, is there a lot of code duplication, code smells, classic refactoring signals.</a> <a data-t="629">And to be able to tell an agent, like, there's code duplication in this file or these tests, like, seems like this test suite could benefit from test fixtures.</a> <a data-t="634">And to be able to work at that high level of being able to speak in the language of refactoring and clean code and to be able to go and reformulate whole parts of a software project in small amounts of time has given me, like, a tremendous sense of agency.</a></p>

<p><a data-t="670">The downside, of course, is that when the agents are working on, you know, the essential parts of the system, they have a difficult time distinguishing between the essential complexity and the accidental complexity.</a> <a data-t="680">And they also generate new kinds of accidental complexity in doing the work that you need them to do.</a> <a data-t="688">And so this could take the form of, you know, creating the right, having the wrong domain model, like, the right, you know, the wrong layering of classes or, like, failing to recognize that, you know, if you're building something UI related that you have to explain to the agent, like, we're using, you know, this is the model, this is the view, this is the controller.</a> <a data-t="712">But if you don't explain that to them and articulate, like, this is how the system should be designed, the default output in a lot of cases is just going to be a hairball that becomes, you know, increasingly difficult for the agents to refactor.</a></p>

<p><a data-t="721">And this gets worse and worse as time goes on because fresh agent sessions come into the existing code base and they're just as happy to, you know, bolt another appendage onto the Frankenstein rather than taking a step back and saying, okay, what is this code, how should this code really be designed?</a> <a data-t="732">You know, what types of, what are the right abstractions, like, the right layering of components to make this easy to test and maintainable, easy to refactor, easy to think about.</a> <a data-t="752">So it's very difficult because, you know, the agents, they've been, you know, reinforcement learned and reward hacked to just want to solve the problem that you put in front of them.</a> <a data-t="762">And so if you need, if you want them to clean up and improve the quality of the code base, generally you have to ask them to do that explicitly.</a> <a data-t="772">They won't just do it on their own.</a></p>

<p><a data-t="773">Another closely related idea to this that I, you know, I have to mention is Conway's law, the idea that the software projects resemble the organizational structures that produce them.</a> <a data-t="788">And so, you know, this is also one of the reasons why small teams often outperform large teams, because you have like a smaller group of people designing the whole system thinking in a coherent manner.</a> <a data-t="804">Whereas when you say, okay, this person is responsible for the data plane, this, this, you know, this team is responsible for the UI, this, you know, team for some other part of the system, you end up having like a lot of, a lot of negotiation and a lot of discordance and kind of the interactions between, between those systems.</a> <a data-t="830">And that makes, generally makes the software projects a great deal more complex and hard, hard to work with.</a></p>
