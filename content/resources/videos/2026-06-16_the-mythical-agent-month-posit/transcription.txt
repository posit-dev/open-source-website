<h3>Fred Brooks and the Mythical Man-Month</h3>

<p><a data-t="208">So if you've never heard about Fred Brooks, he was at IBM and led one of the largest software projects of the 20th century, building OS360, IBM mainframes.</a> <a data-t="224">This led him to write the Mythical Man-Month in 1975, which you say, wow, 1975 is a long time ago, 51 years.</a> <a data-t="230">Still is enduringly one of the most cited and most influential works on software management and software engineering in history.</a> <a data-t="238">And even today you're starting to see, you know, I wrote an essay about the Mythical Man-Month, like Martin Fowler just wrote an essay about it.</a> <a data-t="247">It is still influencing minds and it is coming up more and more in today's context of agents carrying an increasingly large burden of the software that we're writing.</a> <a data-t="262">He wrote a follow-up essay to the Mythical Man-Month that was also very influential called No Silver Bullet, which introduces, I think, a helpful framework in thinking about software complexity that I will come back to and explain.</a></p>

<p><a data-t="279">But if you've never read this book, and I admit that I have never actually read this book cover to cover.</a> <a data-t="284">I've mainly read excerpts and sections and quotes and ideas, but a lot of these ideas, some of which have been lost and have to be relearned over and over again.</a> <a data-t="292">But, you know, Brooks's Law, the idea that adding manpower to a late software project makes it later, it makes it later.</a> <a data-t="302">It's one of those things that, you know, people forget and then they have to relearn the hard way.</a> <a data-t="307">I don't know if any of you have been in a company where a pointy haired boss says, this project is behind, we need to hire engineers to make it go faster.</a> <a data-t="316">I'm usually the person in the room who's saying, wait, wait, like, have you read the Mythical Man-Month?</a> <a data-t="319">Like, are you sure that this is a good idea?</a> <a data-t="319">Maybe the problem is actually that you have the wrong people working on the project, not that you need to add people.</a></p>

<p><a data-t="327">And so this idea of the surgical team that a small team of elite people outperform large teams of average ones is also one of the reasons why startups can deliver innovations and disrupt industries in, you know, short amounts of time and run circles around their much larger and more well-equipped competitors.</a> <a data-t="346">One of the reasons that adding people to a software project can make it go slower is because of the communication overhead, which grows quadratically with the number of people.</a> <a data-t="357">And so, you know, a 20 person software, 20 person engineering team versus a five person engineering team, there's just a lot more overhead in, you know, delegating work, splitting up tasks, going through design, getting everybody on the same page.</a> <a data-t="371">You need to introduce layers of management to keep people on track.</a> <a data-t="371">And, you know, the whole, you know, agile practice was created to try to mitigate some of these issues.</a> <a data-t="377">And, you know, I would argue that the practice of agile is practically dead today and any team that's still having backlog grooming and sprint planning is doing it wrong.</a></p>

<h3>Essential vs. accidental complexity</h3>

<p><a data-t="492">So in the No Silver Bullet essay in 1986, Brooks introduced this idea of two kinds of software complexity, the essential complexity, which is basically what the system solves, how it needs to be designed in order to be a working solution for what you're trying to build.</a> <a data-t="515">And that involves the conceptual integrity and having a coherent picture of like these are the essential set of features for this to be a complete system.</a> <a data-t="521">If we take anything out, the project is no longer a solution for what we're trying to solve.</a> <a data-t="526">And then accidental complexity is everything else that is introduced by our tools and processes and technologies that we're using to build the system.</a> <a data-t="539">And so that involves our programming languages, our build tools, like all of our systems that do testing and QA and continuous integration, you know, the boilerplate that's involved with interacting with databases and all that fun stuff.</a></p>

<p><a data-t="554">And so agents are tremendously powerful tools for dealing with all of this accidental complexity that comes up while you're building a software project.</a> <a data-t="561">You can say, you know, hey, Claude, hey, Codex, you know, hey, Gemini sometimes, go and refactor, you know, all of this code, change the test framework, rewrite all of the tests.</a> <a data-t="574">It's happy to dive in and attack and deal with all of this complexity that is introduced by, you know, the tools and systems that you're using to build the project.</a> <a data-t="585">And I'm encountering this firsthand myself as I've largely moved on to use other programming languages other than Python, which I will show you in more graphic detail in a little while.</a> <a data-t="596">I've never written a line of Go professionally or a line of Swift professionally.</a></p>

<p><a data-t="603">And yet I'm, you know, in any given day, I might be slinging, you know, 5 or 10 or 20,000 lines of code in these programming languages.</a> <a data-t="607">I'm not an expert in, like, what are the right tools and frameworks and libraries that I should be using in each language.</a> <a data-t="611">But, you know, I do look at the code and see whether, like, is there a lot of code duplication, code smells, classic refactoring signals.</a> <a data-t="623">And to be able to tell an agent, like, there's code duplication in this file or these tests, like, seems like this test suite could benefit from test fixtures.</a> <a data-t="629">And to be able to work at that high level of being able to speak in the language of refactoring and clean code and to be able to go and reformulate whole parts of a software project in small amounts of time has given me, like, a tremendous sense of agency.</a> <a data-t="645">And what used to be, like, I'd have to pick and choose my battles of, like, do I really want to spend today refactoring this test suite?</a> <a data-t="650">Usually the answer is no.</a> <a data-t="654">But now I can have, you know, the agents refactor my test suite while I'm having lunch.</a> <a data-t="659">And that's a nice thing.</a></p>

<p><a data-t="659">The downside, of course, is that when the agents are working on, you know, the essential parts of the system, they have a difficult time distinguishing between the essential complexity and the accidental complexity.</a> <a data-t="673">And they also generate new kinds of accidental complexity in doing the work that you need them to do.</a> <a data-t="680">And so this could take the form of, you know, creating the right, having the wrong domain model, like, the right, you know, the wrong layering of classes or, like, failing to recognize that, you know, if you're building something UI related that you have to explain to the agent, like, we're using, you know, this is the model, this is the view, this is the controller.</a> <a data-t="703">But if you don't explain that to them and articulate, like, this is how the system should be designed, the default output in a lot of cases is just going to be a hairball that becomes, you know, increasingly difficult for the agents to refactor.</a></p>
