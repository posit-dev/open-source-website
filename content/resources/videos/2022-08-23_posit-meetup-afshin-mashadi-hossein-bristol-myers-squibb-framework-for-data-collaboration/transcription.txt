<h3>Defining data product</h3>

<p><a data-t="283">So to start things off, I think it's</a> <a data-t="286">quite critical to provide a definition of data product</a> <a data-t="292">and data as a product.</a> <a data-t="294">If you have heard of this term, you</a> <a data-t="296">might have noticed that in different circles,</a> <a data-t="300">in different groups, it could mean quite different concepts.</a> <a data-t="305">How we are defining data product</a> <a data-t="308">is simply a data object that, much like any other products,</a> <a data-t="315">come with a set of characteristics or attributes.</a></p>

<p><a data-t="319">So specifically, we call data product,</a> <a data-t="327">this notion of data product, to be a data object that</a> <a data-t="329">is use case driven.</a> <a data-t="331">This is in contrast with, quote unquote,</a> <a data-t="334">wrangled data that can serve any purpose.</a> <a data-t="336">It's clean data, and you can use it for whatever purpose.</a> <a data-t="339">So this has to be, the data product</a> <a data-t="341">has to have a specific user story or a set of coherent</a> <a data-t="346">objectives that it achieves.</a></p>

<p><a data-t="348">Now, if you have that level of specificity,</a> <a data-t="351">you can imagine that you may have slightly different use</a> <a data-t="354">cases leading to a variety of different data objects.</a> <a data-t="360">So it becomes even more critical to be able to version control</a> <a data-t="363">it and track it.</a> <a data-t="364">So as you have different, slightly different data sets,</a> <a data-t="367">you should be able to branch it.</a> <a data-t="369">You should be able to version track it.</a> <a data-t="371">So making it use case specific and being able, then,</a> <a data-t="376">to branch it and version track it becomes quite critical.</a></p>

<p><a data-t="381">It needs to be tested.</a> <a data-t="382">It needs to be reproducible.</a> <a data-t="385">And I would say not only reproducible, but easily</a> <a data-t="388">reproducible, meaning that with a handful of commands,</a> <a data-t="391">you can just reproduce the data.</a> <a data-t="393">It should be easily maintainable, extensible.</a> <a data-t="396">Think about this as your typical R package in this context.</a></p>

<p><a data-t="402">So in this context of R users, you</a> <a data-t="405">can use an R package for whatever end</a> <a data-t="407">that you have in your analysis or otherwise.</a> <a data-t="410">You can also use that to integrate it</a> <a data-t="412">into a new R package and build upon it and extend it.</a> <a data-t="415">Same should apply to data products.</a> <a data-t="417">You should be able to integrate it into a new data product,</a> <a data-t="421">bring a few of them together, build upon them, extend them.</a> <a data-t="424">So it should be extensible.</a></p>

<p><a data-t="426">It should be findable, accessible, and portable.</a> <a data-t="429">And notes on that last one is that as data scientists,</a> <a data-t="434">if I may speak for a lot of us, that we may not necessarily</a> <a data-t="439">be super conscious or have concerns about whether my data</a> <a data-t="446">is coming from Azure or AWS S3 or whatever platform,</a> <a data-t="450">whatever infrastructure I have.</a> <a data-t="454">But our colleagues in IT or other places, they may.</a> <a data-t="458">So as my data, as the requirements</a> <a data-t="461">of my organization changes, I need</a> <a data-t="463">to take my data from, let's say, AWS S3 to Azure or vice versa</a> <a data-t="468">or to some network drive.</a></p>

<p><a data-t="470">All of these characteristics that we talked about</a> <a data-t="472">should go along.</a> <a data-t="473">So it shouldn't be something that</a> <a data-t="475">is dependent on the platform or technology</a> <a data-t="477">outside of the data product.</a> <a data-t="480">These core set of features, there</a> <a data-t="481">could be other features that are dependent on the platform.</a> <a data-t="485">So these core set of characteristics and attributes</a> <a data-t="490">define what we call a data product.</a></p>

<h3>Data as a product: the framework</h3>

<p><a data-t="495">Now, data as a product is a framework</a> <a data-t="498">to make it practical for data science teams</a> <a data-t="501">to pull together their data wrangling efforts</a> <a data-t="504">towards collaboratively building data products.</a> <a data-t="507">So on one hand, we have this product.</a> <a data-t="512">On the other hand, we have a set of processes</a> <a data-t="514">that allows us to easily, or at least methodically,</a> <a data-t="520">build these data products.</a></p>

<p><a data-t="522">So the processes could be agreements between the teams,</a> <a data-t="526">like how we want to use the conventions of coding,</a> <a data-t="532">as well as some automations and tools that allow us</a> <a data-t="536">to implement those agreements.</a> <a data-t="538">So data as a product, you can think about as a framework,</a> <a data-t="542">way of thinking, as well as the tool sets</a> <a data-t="545">that allow us to implement that way of thinking.</a> <a data-t="548">Data product is the output.</a></p>

<h3>The 80-20 rule and motivations</h3>

<p><a data-t="550">So with that out of the way, as far as the definition goes,</a> <a data-t="555">looking at these attributes, perhaps it's</a> <a data-t="557">not difficult to imagine a variety of motivations</a> <a data-t="560">why a data science team may be interested in adopting</a> <a data-t="565">a framework that will lead to their data sets or data</a> <a data-t="569">objects coming out with all of these attributes.</a> <a data-t="572">But to focus on one, perhaps you can</a> <a data-t="574">think about this 80-20 rule of data science, which</a> <a data-t="577">is basically this observation made by a lot of the data</a> <a data-t="581">scientists that a typical week could involve four days out</a> <a data-t="587">of that five working days that you are engaged in data</a> <a data-t="593">processing or data wrangling, whatever you call it.</a> <a data-t="598">And then on that last day, you may get a chance</a> <a data-t="601">to actually do your data analysis.</a></p>

<p><a data-t="602">So as a data scientist or leader of a data science team,</a> <a data-t="611">if you are interested in adding more agility</a> <a data-t="613">to your overall team efforts, it</a> <a data-t="622">is fair to look at this data processing</a> <a data-t="625">and try to bring in additional agility to it</a> <a data-t="629">and efficiency to it.</a></p>

<p><a data-t="631">And there are a variety of approaches</a> <a data-t="636">that teams have implemented.</a> <a data-t="638">Hopefully, we all work in teams that heroic data wrangling</a> <a data-t="643">is not one of those approaches.</a> <a data-t="645">No one is advocating for shrinking that 80% to 30%</a> <a data-t="651">by just willpower and working extra hours.</a> <a data-t="655">Hopefully, that is not the case.</a> <a data-t="657">But then there are things like new data agreements</a> <a data-t="659">that you may put in place with data vendors.</a> <a data-t="661">You may ask your data platform to do more</a> <a data-t="664">in the way of data validation.</a> <a data-t="666">Even pushing that validation of data</a> <a data-t="669">further upstream into your pipelines, that could help.</a></p>

<p><a data-t="673">In some cases, it may seem appealing or maybe appealing</a> <a data-t="677">to extend the capacity of your data science team</a> <a data-t="681">if the resource is limited within the data science team</a> <a data-t="684">to extend the capacity of the data science team</a> <a data-t="686">by bringing additional resources that could then</a> <a data-t="689">help with just the task of building data.</a> <a data-t="693">However, one caveat around that is, particularly</a> <a data-t="697">in the case of pharma, you can think</a> <a data-t="700">about how much domain knowledge and expertise is needed</a> <a data-t="706">and gets factored in as we are processing the data.</a> <a data-t="709">So science and context can be missed.</a> <a data-t="712">And so that is a caveat.</a></p>

<p><a data-t="714">But setting that aside, these ideas</a> <a data-t="717">as similar approaches collectively</a> <a data-t="720">perhaps provide some level of relief.</a> <a data-t="724">Perhaps a slightly different view</a> <a data-t="727">would be rather than seeking relief,</a> <a data-t="731">we can acknowledge that here's my team spending</a> <a data-t="734">their precious time and resources and expertise.</a> <a data-t="738">I should emphasize that expertise part.</a> <a data-t="741">Building something, so there's a lot of value in that.</a></p>

<p><a data-t="745">If 80% of my team is building this artifact or output,</a> <a data-t="752">that has a lot of value in it.</a> <a data-t="754">So instead of thinking about or along the way</a> <a data-t="759">of thinking about reducing that time to getting that,</a> <a data-t="763">can I also think about how can I drive more value</a> <a data-t="768">from this precious resource?</a> <a data-t="770">And if I'm thinking in that sense,</a> <a data-t="773">I'm not trying to remove the burden of this effort.</a> <a data-t="779">I'm just trying to drive more value from it.</a></p>

<blockquote><a data-t="779">I'm just trying to drive more value from it.</a></blockquote>

<p><a data-t="781">But to alleviate that burden, help with that,</a> <a data-t="785">I can also make collaboration easy.</a> <a data-t="786">So that big lift is shared across the team.</a> <a data-t="790">So it becomes a little bit easier.</a> <a data-t="792">So you make collaboration easy.</a> <a data-t="794">When permissible, you can add a dash of automated standards</a> <a data-t="800">and make, put in place processes, process frameworks</a> <a data-t="806">for collaboration.</a></p>

<p><a data-t="807">So not surprisingly, perhaps at this point,</a> <a data-t="810">you can imagine that this latter approach of driving more value</a> <a data-t="813">from data wrangling is what the framework of data</a> <a data-t="818">as a product, as we are defining it, advocates.</a> <a data-t="821">So the idea is that you're bringing in your usual input</a> <a data-t="824">data, and you're adding your logic of data wrangling.</a> <a data-t="828">And then you feed it into this process</a> <a data-t="829">that out would come a data product, which</a> <a data-t="832">then can be fed into a number of utilities, analysis, apps,</a> <a data-t="838">automated reports.</a> <a data-t="839">And this data product now is reusable and extensible.</a> <a data-t="841">So that work is essentially something that lives on.</a></p>

<p><a data-t="846">That in contrast with a typical workflow of a data scientist,</a> <a data-t="851">which may include data wrangling,</a> <a data-t="854">be so inseparably intertangled with your utility,</a> <a data-t="859">be it analysis or otherwise, that once that analysis is done</a> <a data-t="862">or once that utility has run its course,</a> <a data-t="865">then that piece of data work is essentially</a> <a data-t="868">disposable.</a> <a data-t="869">So you have an expensive, very, very expensive effort</a> <a data-t="873">that now has no more use.</a></p>

<p><a data-t="877">So up to this point, we have talked</a> <a data-t="878">about this notion of data product in abstract.</a> <a data-t="881">So let's think about what's our north star.</a> <a data-t="885">What are we aiming for here?</a> <a data-t="886">So as I alluded to earlier, it has</a> <a data-t="889">to serve a coherent set of objectives.</a> <a data-t="891">So this is one of the core requirements.</a> <a data-t="893">Again, thinking about any product out there.</a> <a data-t="895">If you have a vacuum cleaner, it's</a> <a data-t="898">not going to be a hairdryer or an iron.</a></p>
<!-- segment separator -->
<p><a data-t="902">So it has to have a coherent set of objectives.</a> <a data-t="906">So that limits the scope of the effort.</a></p>

<p><a data-t="912">Even with a limited scope, you don't</a> <a data-t="913">want to be building it from A to Z all in one shot.</a> <a data-t="917">So think about, again, a product.</a> <a data-t="919">Like you may have different components</a> <a data-t="921">that you build and you assemble.</a> <a data-t="922">It has to be built modularly.</a></p>

<p><a data-t="926">And if you are building it modularly</a> <a data-t="927">and your buddy here is building some parts</a> <a data-t="929">and you are building some parts of it</a> <a data-t="931">and you're bringing it all together,</a> <a data-t="933">it should be something that, while not totally</a> <a data-t="938">setting the stone that you're doing exactly this way,</a> <a data-t="941">it has to have, it shouldn't be something that is an art</a> <a data-t="944">and everybody does it their own way.</a> <a data-t="945">So collaboration requires some blueprint</a> <a data-t="948">of how we are building these elements.</a></p>

<p><a data-t="952">Now, again, collaboration requires everything</a> <a data-t="955">to be versioned so we don't get tangled up</a> <a data-t="957">in what version of what elements we are</a> <a data-t="961">talking about across the team.</a> <a data-t="963">So by everything here, I mean code, environment, and data</a> <a data-t="966">needs to be versioned.</a></p>

<p><a data-t="967">So all of the things that I've talked about so far,</a> <a data-t="970">as far as the requirements of the product,</a> <a data-t="971">has to do with the build process.</a> <a data-t="973">But from a user perspective, it also has to be easy to use.</a> <a data-t="976">So connect, list, get is all you need</a> <a data-t="979">to be able to pull the data down and use it.</a> <a data-t="982">So as a user, you should have an easy interface.</a></p>

<p><a data-t="984">And lastly, as I mentioned, we want</a> <a data-t="986">to have it be platform agnostic.</a> <a data-t="989">So if you're going from S3, later on you</a> <a data-t="991">need to go to file systems and RStudio Connect</a> <a data-t="994">is your next destination.</a> <a data-t="996">The data science workflow should dictate where your data is</a> <a data-t="1000">or if there are other requirements that</a> <a data-t="1003">can be accommodated and you don't</a> <a data-t="1004">have to worry about the functionality of your data</a> <a data-t="1007">being compromised.</a></p>

<h3>Build tool requirements</h3>

<p><a data-t="1009">Now, this is the product's requirement.</a> <a data-t="1012">And there should be a build tool that</a> <a data-t="1014">can enable building that product according to those attributes.</a> <a data-t="1018">So you can see the linkage here that a build tool,</a> <a data-t="1024">given all those attributes that I mentioned are requirements,</a> <a data-t="1027">should naturally support modular development,</a> <a data-t="1029">should minimize boilerplate, should enable reproducibility</a> <a data-t="1033">by capturing everything in the state of the code, data,</a> <a data-t="1037">and environment, should encourage best code style</a> <a data-t="1041">practices, should enable full traceability of everything,</a> <a data-t="1045">code, data, environment.</a> <a data-t="1046">And as a builder, you should not be learning a new language.</a> <a data-t="1050">If you know R, if you know Git, you should be good to go.</a></p>

<p><a data-t="1052">Now, if this was instead of a data as a product,</a> <a data-t="1056">this was software as a product, you</a> <a data-t="1059">would rightly expect that the tool is already around.</a> <a data-t="1065">And in the rich set of tools and experiences and processes</a> <a data-t="1071">that have been developed and implemented</a> <a data-t="1074">by DevOps community, when we are talking about the software,</a> <a data-t="1078">we can accommodate all of those features of a build tool.</a></p>

<p><a data-t="1083">The difference here is that not only we have code,</a> <a data-t="1087">but we have data.</a> <a data-t="1088">So this gives us an inspiration that if we</a> <a data-t="1090">were able to capture data as code,</a> <a data-t="1093">we would then build a bridge to this rich set of tools</a> <a data-t="1099">and experiences that are available in the DevOps</a> <a data-t="1103">community and put those to use for our end.</a></p>

<blockquote><a data-t="1088">So this gives us an inspiration that if we</a> <a data-t="1090">were able to capture data as code,</a> <a data-t="1093">we would then build a bridge to this rich set of tools</a> <a data-t="1099">and experiences that are available in the DevOps</a> <a data-t="1103">community and put those to use for our end.</a></blockquote>

<h3>Data as code: a conceptual walkthrough</h3>

<p><a data-t="1108">So building with data as a code, what's the approach here?</a> <a data-t="1114">So thinking about the concept there.</a> <a data-t="1117">Let me walk through an example of how</a> <a data-t="1120">this could work conceptually.</a></p>

<p><a data-t="1122">So let's say you are here in this point one.</a> <a data-t="1126">You have some data sets.</a> <a data-t="1127">Some of you in pharma are familiar</a> <a data-t="1128">with this nomenclature.</a> <a data-t="1129">So let's say you have some LV data, which</a> <a data-t="1131">is this lab data collected on a cohort of patients.</a> <a data-t="1134">You have some medication data and a bunch more data sets</a> <a data-t="1139">that you have at your disposal.</a></p>
