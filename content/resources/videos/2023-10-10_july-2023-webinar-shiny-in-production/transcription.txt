<h3>Optimizing your Shiny app</h3>

<p><a data-t="1056">Alright, so now that we've profiled our Shiny application, right, and then going back to our restaurant, you start thinking of some ways of how we can improve our chefs kind of operations.</a> <a data-t="1070">So maybe we have the chef prepare the ingredients in advance, or maybe someone else in the kitchen can prepare those ingredients in advance.</a> <a data-t="1076">That way, not to spend the time preparing them as orders come in.</a> <a data-t="1080">Maybe we just keep the kitchen organized and updated, making sure the chef knows exactly where all the tools are, and making sure they have the best tools for the job.</a> <a data-t="1091">Prepare the most popular meals in advance.</a> <a data-t="1097">And then also multitasking, like training your chef to prepare two, maybe three meals at the exact same time.</a></p>

<p><a data-t="1103">So we're going to go through each one of those steps, we're going to talk about it in the context of our Shiny restaurant, and then how that translates over to our Shiny application.</a> <a data-t="1113">And we're going to start with preparing ingredients in advance.</a> <a data-t="1117">So again, let's say your chef, they get an order for a ham and cheese sandwich.</a> <a data-t="1123">And when that order comes in, if this is their starting material, this raw material, they're gonna have to spend some time cutting tomatoes, slicing the bread, slicing the ham, and that's going to take time.</a> <a data-t="1133">And what would be much faster is if this was their starting material, all the ingredients were prepared in advance, they can simply grab each component, assemble the sandwich super quick, and then deliver it to the end user or the customer.</a></p>

<p><a data-t="1147">So for Shiny apps, this essentially means preparing your data in advance.</a> <a data-t="1147">And 99% of all times when you have slow Shiny applications is likely because the data is too large.</a> <a data-t="1155">And you know, sometimes that's going to be kind of unavoidable.</a> <a data-t="1162">But other times we can prepare that data in advance, so that only the data that's needed for that Shiny application is processed.</a> <a data-t="1171">So a few different things to consider.</a> <a data-t="1171">Make sure when you're reading a data to your Shiny application that you read and process that data only once.</a> <a data-t="1177">You want to try to not get into a situation where every single time someone slides a bar in your Shiny application, it re-reads in the data, and then re-reads in the data over and over and over again.</a></p>

<h3>Caching outputs</h3>

<p><a data-t="1606">All right, let's go back to our restaurant and talk about another way that we can hopefully improve performance.</a> <a data-t="1610">And that is to prepare the most popular meals in advance.</a> <a data-t="1616">So I think the best way to think about this, let's say your Shiny restaurant is actually a pizzeria.</a> <a data-t="1621">And let's say if 10 people walk into your restaurant, nine of them are going to order your world-famous margarita pizza.</a> <a data-t="1630">So because of that, you start to think, well, okay, maybe I can start preparing a bunch of margarita pizzas in advance when I first open up my doors.</a> <a data-t="1635">And that way, when people enter the front door, I can just quickly deliver that already prepared margarita pizza.</a> <a data-t="1646">So essentially, you can have all these margarita pizzas in this hotbox, ready to be delivered instantaneously.</a></p>

<p><a data-t="1649">So for Shiny applications, this essentially means caching your outputs.</a> <a data-t="1655">And some of you may be familiar with this, but what is caching your outputs?</a> <a data-t="1661">What Shiny will do is it'll store that combination of your input and outputs, so kind of the output of these render and reactive functions.</a> <a data-t="1667">And if the application, if it sees that input, it'll generate the resulting output only once, and then it will store that output in a cache.</a> <a data-t="1677">And if those inputs are seen again, it can simply retrieve that value or that plot from the cache instead of having to recompute it over again.</a></p>

<p><a data-t="1691">Let me show you kind of conceptually how this works.</a> <a data-t="1691">So here we have a render plot function.</a> <a data-t="1697">So I'm generating a plot here of the state of Maryland, which is where I live here in the United States.</a> <a data-t="1701">And to generate this plot, it just takes a single input right up here, where I input the state Maryland.</a> <a data-t="1707">So let's say this takes about four seconds to compute.</a> <a data-t="1707">Not super slow, but you know, still four seconds, the user is going to have to wait.</a> <a data-t="1714">So what I can do instead is I can take this render plot function and I can pipe it into the bind cache function.</a> <a data-t="1719">It's going to take that single state input.</a> <a data-t="1724">That way, when I go to indirect to this application, I select Maryland, it generates this plot once, which takes four seconds, and then it caches that plot.</a> <a data-t="1731">And then if another user or my future self comes back to this application and selects Maryland, rather than having to regenerate the plot, it can just grab the plot from the cache and deliver it in a fraction of the time.</a></p>
