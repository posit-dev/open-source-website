<h3>Composable data systems</h3>

<p><a data-t="391">All right, composable data systems.</a> <a data-t="394">Last year at VLDB, I collaborated with fine folks at Meta to write this paper called</a> <a data-t="402">The Composable Data Management System Manifesto.</a> <a data-t="406">It's a great paper.</a> <a data-t="408">I want to help you in this talk by presenting some of the key ideas from the paper and why</a> <a data-t="415">they matter.</a> <a data-t="417">I do recommend that you check out this paper.</a> <a data-t="419">I think it's really well written.</a></p>

<p><a data-t="423">The Meta folks did most of the writing, but it's very well written and I think lays out</a> <a data-t="429">a really compelling vision for where things are going.</a></p>

<p><a data-t="435">What is a composable data system?</a> <a data-t="438">The way that I think about this is that we are building systems based on open standards</a> <a data-t="444">and protocols.</a> <a data-t="446">We're designing for modularity, reuse, and interoperability with other systems that share</a> <a data-t="451">those common interfaces in open standards and protocols.</a> <a data-t="455">In particular, we're resisting this idea of vertical integration where every layer of</a> <a data-t="462">your system is bespoke and you build it yourself.</a> <a data-t="465">It's this homespun thing where you build everything top to bottom.</a></p>

<p><a data-t="469">It does create more work in some ways because you have to deal with coordination and open</a> <a data-t="474">source diplomacy.</a> <a data-t="476">You have to think about moving along these different pieces that you share governance</a> <a data-t="480">and you share ownership with other developers and people who are working on different layers</a> <a data-t="484">of the stack.</a> <a data-t="487">The hope is that over time that each of the component pieces that we use to build these</a> <a data-t="492">systems become so much better, easier to use, faster, more interoperable, and that you end</a> <a data-t="499">up creating a solution that is a lot more future-proof and delivers better results over</a> <a data-t="508">time.</a></p>

<p><a data-t="510">It's a little bit painful because you have to go through the painful growing pains of</a> <a data-t="518">creating these new systems and making them all work together as well as negotiating with</a> <a data-t="522">all of the open source developers that are involved in these projects.</a> <a data-t="526">The way that it was put in the words in the paper is that we envision by decomposing data</a> <a data-t="531">management systems into a more modular stack of reusable components, the development of</a> <a data-t="537">engines can be streamlined while reducing maintenance costs and ultimately providing</a> <a data-t="541">a more consistent user experience.</a></p>

<p><a data-t="545">By clearly outlining APIs and encapsulating responsibilities, data management software</a> <a data-t="551">could more easily be adapted, for example, to leverage novel devices and accelerators</a> <a data-t="556">as the underlying hardware evolves.</a> <a data-t="559">That was one of the reasons why we founded Voltron Data.</a> <a data-t="563">We observed that it's hard for people to take advantage of GPUs to accelerate their systems.</a> <a data-t="569">We also saw that there's many new hardware companies creating new types of hardware.</a> <a data-t="575">We need to make a corresponding investment in the software layer to make it easier to</a> <a data-t="580">take advantage of new developments in hardware, whether that's faster computing, faster</a> <a data-t="585">networking, faster storage.</a></p>

<p><a data-t="588">Ideally, from the standpoint of you as a user, you just want to be able to write Python code</a> <a data-t="592">and as the hardware improves, all your software gets faster and you don't have to think about</a> <a data-t="596">the messy details of, well, how do I take advantage of this bleeding edge development</a> <a data-t="600">in computing hardware?</a></p>

<p><a data-t="604">The hope is that by relying on a modular stack that reuses execution engines, language front-ends,</a> <a data-t="610">the data systems can provide a more consistent experience and semantics to users from</a> <a data-t="616">transactional to analytic systems, stream processing to machine learning workloads.</a> <a data-t="620">That sounds very nice in principle.</a></p>

<h3>Why composability is happening now</h3>

<p><a data-t="624">One question people have had is, why is this happening now?</a> <a data-t="628">Why is it happening in the 2020s?</a> <a data-t="632">Why didn't this happen in the 2010s or even earlier?</a> <a data-t="636">It helps to go back and think about the generational eras of big data technology going back to the</a> <a data-t="640">original Google MapReduce paper in the mid-2000s.</a></p>

<p><a data-t="646">The clone of Google MapReduce and Google File System as HDFS and Apache Hadoop,</a> <a data-t="652">that was the first release of Hadoop from Yahoo was in 2006.</a> <a data-t="658">The MapReduce paper popularized this idea of disaggregated storage and compute.</a> <a data-t="664">You have a big distributed file system, you have all of your data sets live as files in that file</a> <a data-t="668">system, and then you have a bunch of compute engines that can process on those files.</a> <a data-t="674">You process files in, the systems write files out back into that distributed file system.</a></p>

<p><a data-t="680">But what this created was this collection of monolithic vertically integrated systems</a> <a data-t="686">that were part of the Hadoop ecosystem.</a> <a data-t="690">Just getting these components to a place where they were viable and you could use them to</a> <a data-t="694">productively work was hard enough.</a> <a data-t="700">Thinking about a hierarchy of needs thing, thinking about how we could modularize components</a> <a data-t="706">of those systems and reuse large pieces of software between those systems,</a> <a data-t="712">that was pie-in-the-sky thinking back in the late 2000s, early 2010s.</a></p>

<p><a data-t="718">But there was a big shift in the 2010s where a particular large software vendor shifted from</a> <a data-t="724">selling proprietary vertically integrated software components to delivery of services in a cloud</a> <a data-t="728">environment.</a> <a data-t="734">That also led to an emergence of open source standards, file formats like Parquet,</a> <a data-t="740">as well as there was major progress in computing, networking, and storage.</a> <a data-t="746">Disk drives got a lot faster, networking got a lot faster, processor units.</a> <a data-t="752">In GPUs a little bit, but in GPUs it's continued to go off to the moon</a> <a data-t="758">as Moore's Law has continued in more specialized processor chips.</a></p>

<p><a data-t="768">Through that period, as open standards began to emerge, we started thinking about</a> <a data-t="774">how we could create technologies that would help better take advantage</a> <a data-t="780">of the innovation in the hardware and the hardware layer.</a> <a data-t="786">That has led us in this current era to think about re-architecting all of our systems</a> <a data-t="792">on interoperable standards that will enable us to get much better performance</a> <a data-t="798">and efficiency across a heterogeneous application stack that's doing a mixture</a> <a data-t="804">of ML, feature engineering, machine learning training, and AI inference.</a></p>

<p><a data-t="810">We've had this emergence of new standards for composability, which I will talk about.</a> <a data-t="816">We're seeing simultaneously an emergence of new systems which are built to be</a> <a data-t="822">composable from the ground up, as well as retrofitting existing pieces</a> <a data-t="828">of systems with new components which are created with this new composable mindset.</a></p>

<p><a data-t="836">Back to the paper, we foresee that for composability it's going to cause</a> <a data-t="842">another major disruption to how data management systems are designed.</a> <a data-t="848">We foresee that monolithic systems will become obsolete and give space</a> <a data-t="854">for new ideas.</a></p>

<p><a data-t="860">I was working with the Hadoop ecosystem at the time.</a> <a data-t="866">I was trying to socialize these ideas with the data science community.</a> <a data-t="872">This was my first talk at the New York R Conference in 2015.</a> <a data-t="878">There wasn't a lot of cross-pollination between the data science world</a> <a data-t="884">and the big data world.</a> <a data-t="890">These were ideas from the big data world that we were trying to socialize</a> <a data-t="896">in the data science community.</a></p>
<!-- segment separator -->
<p><a data-t="902">The core idea of this paper is that we've made all of this progress</a> <a data-t="908">in big data systems with impressive scalability, but few of the performance</a> <a data-t="914">benchmarks evaluate their absolute.</a> <a data-t="920">They look just at scalability but without evaluating their absolute performance.</a> <a data-t="926">In this paper, they introduce a metric called cost.</a> <a data-t="932">It's the configuration that outperforms a single thread to try to measure</a> <a data-t="938">the amount of overhead that is introduced into a distributed system</a> <a data-t="944">by enabling it to scale.</a></p>

<p><a data-t="1026">We started imagining what if we had this shared data science run time,</a> <a data-t="1032">a set of libraries and computational systems that we could use interchangeably</a> <a data-t="1038">across programming languages.</a> <a data-t="1044">It didn't matter which language front-end you're using, what programming language.</a></p>

<h3>Architecture of composable systems</h3>

<p><a data-t="1194">If we think about the architecture of what new composable systems look like,</a> <a data-t="1200">on the bottom tier we have...</a> <a data-t="1206">This is a diagram from the paper.</a> <a data-t="1210">We have a modular execution engine,</a> <a data-t="1216">a runtime which provides for distributed computing and coordination.</a> <a data-t="1222">That could be Spark, that could be Ray,</a> <a data-t="1228">or another distributed runtime that makes use of one of these modular engines</a> <a data-t="1234">like DuckDB or Velox or another.</a></p>

<p><a data-t="1238">We create optimized query plans</a> <a data-t="1244">which are handed off into our distributed runtime.</a> <a data-t="1250">There are now several modular execution engines</a> <a data-t="1256">written in different programming languages</a> <a data-t="1262">such as the now Apache Data Fusion meetup.</a> <a data-t="1268">It's a Rust-based modular query engine.</a> <a data-t="1274">It has a query optimizer on the front end as well,</a> <a data-t="1280">but can also be just as an execution engine in Rust.</a> <a data-t="1286">It's a native distributed execution engine in C++</a> <a data-t="1292">that initially is targeting NVIDIA GPUs.</a></p>

<p><a data-t="1298">One of the things that we've developed in this community</a> <a data-t="1304">to make connecting these engines to the language front end easier</a> <a data-t="1310">is to have an intermediate representation for queries.</a> <a data-t="1314">The idea is that your language front end,</a> <a data-t="1318">whether that's a DataFrame API or a SQL API,</a> <a data-t="1322">we translate that into a substrate plan</a> <a data-t="1326">and we can optimize that substrate plan</a> <a data-t="1330">and then the execution engine can take that plan</a> <a data-t="1334">and turn that into a physical execution plan</a> <a data-t="1338">that is sent off to the cluster to be executed.</a></p>

<p><a data-t="1342">We also retrofit existing popular query engines</a> <a data-t="1350">with these new modular accelerators.</a> <a data-t="1354">Three of them that you can get access to</a> <a data-t="1358">or you can look at or contribute to right now.</a> <a data-t="1362">One is Prestissimo, which is retrofitting PrestoDB,</a> <a data-t="1366">I should clarify, not Trino, with Velox.</a> <a data-t="1370">There's Comet, which has been just donated</a> <a data-t="1374">into the DataFusion project from Apple,</a> <a data-t="1378">which is accelerating Spark with DataFusion.</a> <a data-t="1382">There's also Apache Gluten, part of the Apache Incubator,</a> <a data-t="1386">which is accelerating Spark with Velox.</a> <a data-t="1390">Eventually we'll have DataFusion and Presto</a> <a data-t="1394">and probably every combination of modular accelerators</a> <a data-t="1398">in our query engine projects.</a></p>

<p><a data-t="1402">All of this begins to pose the question of</a> <a data-t="1406">why as a user should I be locked into using</a> <a data-t="1410">a particular full-stack query engine like Spark or Presto?</a> <a data-t="1414">The cost, performance, and latency</a> <a data-t="1418">of these different systems varies greatly.</a> <a data-t="1422">We can do a lot with DuckDB.</a> <a data-t="1426">But when you have an actual big problem</a> <a data-t="1430">that's too big for DuckDB,</a> <a data-t="1434">you want to be able to transition gracefully</a> <a data-t="1438">to using that larger scalable execution engine.</a></p>

<p><a data-t="1442">Of course, last year at Data Council</a> <a data-t="1446">we had Jordan Tagani on the stage in a duck costume</a> <a data-t="1450">talking about how big data is dead.</a> <a data-t="1454">Big data still is big data. Big data does still exist.</a> <a data-t="1458">I believe that we should be able to gracefully transition</a> <a data-t="1462">from working at the single machine,</a> <a data-t="1466">could be a large single machine, but the small scale</a> <a data-t="1470">to a large scalable data processing engine</a> <a data-t="1474">without as much pain and suffering.</a></p>

<p><a data-t="1478">This isn't that easy, though, in part because</a> <a data-t="1482">it advertises just standard SQL.</a> <a data-t="1486">Because SQL dialects, while SQL is a standard,</a> <a data-t="1490">in practice SQL dialects are non-portable</a> <a data-t="1494">and they feature a wide spectrum of different features.</a> <a data-t="1498">There's a tool like SQLGLOT, which is amazing,</a> <a data-t="1502">which helps with transpiling and converting from one SQL dialect</a> <a data-t="1506">to another, but this does create a problem.</a> <a data-t="1510">You have to solve this problem because if you have a mountain</a> <a data-t="1514">of existing SQL queries and you want to migrate them</a> <a data-t="1518">to use a different data processing engine,</a> <a data-t="1522">you have to rewrite all those queries and deal with all the quirky edge cases</a> <a data-t="1526">of type coalescing, conversion, and whatnot.</a> <a data-t="1530">Knowing which engine to use in every scenario is non-trivial</a> <a data-t="1534">and may not always be obvious.</a></p>

<h3>Toward a unified API: Ibis and multi-engine stacks</h3>

<p><a data-t="1538">A few years ago in CIDR 2021,</a> <a data-t="1542">folks at Microsoft approached this problem from the standpoint</a> <a data-t="1546">of the Azure data platform to say,</a> <a data-t="1550">could we create a unified API for interacting with all these different database engines</a> <a data-t="1554">that we have available in the Azure platform and intelligently choose</a> <a data-t="1558">which one to use based on the type of workload,</a> <a data-t="1562">like how big the data set is, what statistics we have about the data,</a> <a data-t="1566">performance, good total cost of ownership for the query.</a> <a data-t="1570">They described a research project that they did called Magpie</a> <a data-t="1574">where they created a pandas-like data frame API.</a> <a data-t="1578">They have a compiler and optimizer at the middle.</a> <a data-t="1582">They have a common data layer, which is based on Arrow,</a> <a data-t="1586">that provides for a distributed data fabric to coordinate</a> <a data-t="1590">these different execution engines within the Azure platform.</a> <a data-t="1594">These are the different backends that are available in Azure.</a></p>

<p><a data-t="1598">I love this idea and I would really like to help it become</a> <a data-t="1602">more mainstream and a reality for data engineers everywhere.</a> <a data-t="1606">A project that I've been involved in,</a> <a data-t="1610">I started about nine, almost 10 years ago,</a> <a data-t="1614">and that we've been putting a lot of resources into is the IBIS project in Python,</a> <a data-t="1618">which had been an effort to harmonize the best features of modern SQL</a> <a data-t="1622">with Python's fluent data frame APIs.</a> <a data-t="1626">We also wanted in IBIS to fix shortcomings in the pandas API</a> <a data-t="1630">and make things that are hard to do with pandas a lot easier to do with IBIS,</a> <a data-t="1634">so we made a deliberate choice to depart from the pandas API.</a> <a data-t="1638">We wanted to make it easy to build complex,</a> <a data-t="1642">large analytical SQL queries by using the benefits of a modern</a> <a data-t="1646">programming language, functions and parameters and things like that,</a> <a data-t="1650">things that don't exist in SQL.</a></p>
