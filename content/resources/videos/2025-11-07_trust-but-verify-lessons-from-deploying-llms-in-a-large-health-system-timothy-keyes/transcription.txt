<h3>Introducing Chat EHR (Chatter)</h3>

<p><a data-t="122">This is why our team at Stanford</a> <a data-t="128">Healthcare created an application called Chat EHR or Chatter. Chatter's UI is served by an infrastructure layer that handles all</a> <a data-t="146">the technical things that you need when you're working with LLMs, and this</a> <a data-t="150">infrastructure layer is also exposed on the back end as a suite of REST APIs so</a> <a data-t="155">that data scientists like me can build various task-specific automations to</a> <a data-t="160">guide our patients efficiently through the healthcare system. Some of the things</a> <a data-t="164">that we tend to do with these task-specific automations are screen</a> <a data-t="168">patients for eligibility for certain kinds of appointments, schedule those</a> <a data-t="171">appointments, and then write draft documentation for our clinicians once</a> <a data-t="176">those appointments are completed.</a></p>

<p><a data-t="176">However, this talk is actually not about</a> <a data-t="182">Chatter at all. It is not about how it was built, and it is not about how it</a> <a data-t="187">works. Instead, it is about a single question that faced our team once we put</a> <a data-t="193">this system into production and over 4,000 of our clinicians started using it</a> <a data-t="197">out in the real world for real patient care, and that question is this. How do we</a> <a data-t="203">know that an LLM-powered system is behaving as expected over time, or more</a> <a data-t="208">specifically, how do we know that the text that the LLM is generating is</a> <a data-t="212">reliable, useful, and safe for our patients and the clinicians who serve</a> <a data-t="215">them?</a></p>

<p><a data-t="215">I can't tell you that our team or really anybody else has definitively</a> <a data-t="221">answered this question. <h3>Lesson one: the view from space</h3>

<p><a data-t="228">Sound good? Awesome. This brings us then to lesson</a> <a data-t="235">number one, the view from space. I will claim that LLMs really aren't so</a> <a data-t="241">different from other statistical models in terms of what you really care about</a> <a data-t="244">organizationally once they have been deployed. What I mean by this is that our</a> <a data-t="249">organization has an MLOps framework that we use for all of our statistical model</a> <a data-t="253">deployments, and we were really worried when we started working with LLMs that</a> <a data-t="257">they were just too different of a technology, and they would basically</a> <a data-t="260">smash our framework into smithereens and we would have to start over from scratch.</a> <a data-t="265">Luckily, this didn't happen because we just found in practice that regardless</a> <a data-t="271">of the type of model that you're serving, whether it's logistic regression, XGBoost,</a> <a data-t="275">an LLM, or an agent, there's always certain things that you have to do to</a> <a data-t="282">support a model when it's in production that are kind of regardless of the</a> <a data-t="286">underlying technology.</a></p>

<p><a data-t="286">Let me illustrate this clearly by walking you through</a> <a data-t="290">Stanford HealthCare's MLOps framework. Your organization probably has something</a> <a data-t="295">pretty similar, but if you don't, Julia Silke actually gave a really beautiful</a> <a data-t="298">talk about MLOps in her PositConf talk a couple of years ago, and you should go</a> <a data-t="303">watch that. But at Stanford HealthCare, we break down MLOps into three pillars.</a></p>

<p><a data-t="308">The first we call system integrity. This is about monitoring a model's ability to</a> <a data-t="313">find its input data and to post its output to the intended destination with low</a> <a data-t="317">latency and high availability. This has to do with the IT infrastructure supporting</a> <a data-t="322">your model, so regardless of what that model is, it's always on the table and</a> <a data-t="326">it's something you have to keep track of. The second pillar we call performance.</a> <a data-t="331">This is about monitoring the quality and accuracy of the output of the model.</a> <a data-t="335">So how often is the model correct? How often is it incorrect about the things</a> <a data-t="338">that it does or says? Again, regardless of the model, this is something you have to</a> <a data-t="342">care about if you want to be a good data scientist. And then lastly, our third</a> <a data-t="347">pillar is impact. Because we're a hospital, it's really not enough for our</a> <a data-t="351">models to be technically excellent. They also have to have a traceable way of</a> <a data-t="356">serving our number one goal as an organization, which is providing the best</a> <a data-t="360">patient care possible. So we typically also monitor process measures and KPIs</a> <a data-t="365">that are associated with any of our deployments to make sure that they are</a> <a data-t="368">serving their intended purpose towards this mission.</a></p>

<p><a data-t="368">So we found that these three</a> <a data-t="374">principles, kind of luckily for us, are sufficient for monitoring any model after</a> <a data-t="378">it's been deployed, including LLMs. But that all being said, we did find it most</a> <a data-t="383">difficult to tackle this second pillar. How do you define and then monitor the</a> <a data-t="388">accuracy of an LLM? It's a really sophisticated technology, and it can do</a> <a data-t="393">so many things.</a></p>

<h3>Lesson two: key differences in monitoring LLM performance</h3>

<p><a data-t="393">This brings us to our second lesson. So we are now no longer in</a> <a data-t="399">space. We have re-entered the atmosphere. And as we get closer to the Earth, we can</a> <a data-t="404">appreciate that despite their apparent differences at a high level, there are</a> <a data-t="408">some key differences between LLMs and other kinds of statistical models that</a> <a data-t="412">affect how we define and monitor their performance, just like accuracy element.</a> <a data-t="417">There are a bunch of differences that we could pull apart here between LLMs and</a> <a data-t="421">other types of models, but I will talk about three key differences that we are</a> <a data-t="424">most opinionated about at Stanford.</a></p>

<p><a data-t="424">The first is this. Humans simply interact</a> <a data-t="432">with text differently than they do with the outputs from other kinds of models,</a> <a data-t="435">like probabilities or discrete labels. In a clinical environment, machine learning</a> <a data-t="440">models are typically used to make recommendations to clinicians. So they</a> <a data-t="444">might recommend prescribing a particular medication or ordering a</a> <a data-t="447">certain laboratory test. But in practice, what we found is that unless these</a> <a data-t="452">models are highly, highly accurate, which most of them simply are not, because</a> <a data-t="456">medicine is very hard, clinicians learn not to trust them, and so they ignore</a> <a data-t="461">them. So they end up being not so useful. With LLMs, on the other hand, we find</a> <a data-t="466">that this kind of like magical human-computer interaction dynamic</a> <a data-t="470">emerges where clinicians are actually really eager to read the free text</a> <a data-t="474">recommendation of an LLM and to understand its justification for making</a> <a data-t="479">that recommendation. They kind of like see what the LLM is suggesting to them,</a> <a data-t="482">run it through their own clinical reasoning process, and then decide if</a> <a data-t="486">they agree or disagree with the model.</a></p>

<p><a data-t="486">So what we've learned is that monitoring</a> <a data-t="490">the so-called performance of our LLM deployments is really about capturing</a> <a data-t="495">this human-in-the-loop adjudication process, so that we can track over time</a> <a data-t="498">how much our expert clinicians are agreeing with the things that the LLM</a> <a data-t="502">says.</a></p>

<blockquote><a data-t="486">So what we've learned is that monitoring</a> <a data-t="490">the so-called performance of our LLM deployments is really about capturing</a> <a data-t="495">this human-in-the-loop adjudication process, so that we can track over time</a> <a data-t="498">how much our expert clinicians are agreeing with the things that the LLM</a> <a data-t="502">says.</a></blockquote>

<p><a data-t="502">I think this is well illustrated by an example, so I'll walk you through one</a> <a data-t="508">of our LLM deployments to give you a flavor for how this looks in practice.</a> <a data-t="513">The task here is we're asking the LLM to identify patients who might benefit from</a> <a data-t="520">an appointment with a specialist, just a certain kind of physician, basically. So</a> <a data-t="525">our starting point is a prompt, and that prompt contains the criteria for the</a> <a data-t="529">specialist appointment. It usually contains some information about the</a> <a data-t="532">types of illnesses that the specialist can treat. We send this to the LLM along</a> <a data-t="537">with clinical notes describing the health of the patient and ask the LLM to</a> <a data-t="541">output two things. The first is a targeted recommendation for whether the</a> <a data-t="546">patient should get the specialist appointment, and the second is a</a> <a data-t="550">justification with cited evidence from the patient's chart of why it made that</a> <a data-t="555">recommendation. Both of these are then sent to one of our expert clinicians who</a> <a data-t="560">are always in the loop, and that clinician then decides if they agree or</a> <a data-t="563">disagree with the model and if they want to place the referral for the</a> <a data-t="567">specialist appointment.</a></p>

<p><a data-t="567">Our monitoring approach then really hinges on capturing</a> <a data-t="572">this clinician's decision within our electronic health record, and then we</a> <a data-t="576">track it over time so that if we see basically that the disagreement rate of</a> <a data-t="580">our clinicians is increasing for a deployment after some period of</a> <a data-t="585">time, this basically suggests that something is going wrong, maybe</a> <a data-t="588">documentation practices have changed, maybe we need to adjust the prompt, and</a> <a data-t="592">that our data science team then needs to remediate that.</a></p>

<p><a data-t="592">Okay, so moving on to our</a> <a data-t="598">second key difference between LLMs and other statistical models in terms of</a> <a data-t="602">monitoring performance. Whereas the first one was more conceptual, this one is more</a> <a data-t="606">technical. It has to do with like some engineering things, and it's based on the</a> <a data-t="610">observation that frontier LLMs developed by large companies like ChachiPT,</a> <a data-t="614">Claude, and Gemini are externally developed and versioned by third parties.</a> <a data-t="619">So this means that they actually update and deprecate over time without your</a> <a data-t="623">team necessarily being in control. This is in contrast to something like an XGBoost</a> <a data-t="627">model that you may have trained, hosted, and served yourself, which will</a> <a data-t="631">only ever be updated or retrained or deprecated, turned off, when you choose.</a></p>

<p><a data-t="636">You may not think about this as being related to monitoring a model</a> <a data-t="641">post-deployment in the traditional sense, but my point here is that when you're</a> <a data-t="645">working with proprietary LLMs, you don't just have to worry about the data</a> <a data-t="650">distributions of your deployed population shifting over time, you don't</a> <a data-t="654">just have to worry about the user behavior changing over time, you</a> <a data-t="657">actually also have to worry about the model itself changing over time as it's</a> <a data-t="661">continually updated by the third party that has developed it. So what we do</a> <a data-t="666">about this is basically host a suite of internally developed benchmarks that</a> <a data-t="671">help us to monitor task performance for important tasks at Stanford Healthcare</a> <a data-t="674">whenever a new model is released. So for those of you who might be familiar, GPT-5</a> <a data-t="679">was released a couple of weeks ago, and we were curious like, should we</a> <a data-t="683">switch to this model? We're using a couple of legacy models that won't be</a> <a data-t="686">supported in a couple of months, and so this is our approach for dealing with</a> <a data-t="690">that scenario.</a></p>

<p><a data-t="690">For those of you keeping me honest, I have used some jargon here.</a> <a data-t="695">So benchmark is a term that is used commonly in the LLM world, and the LLM</a> <a data-t="702">world like really likes jargon, but to keep it short and sweet, a benchmark is</a> <a data-t="705">essentially a human-labeled gold-standard test data set for a</a> <a data-t="710">specific task. So if you remember our specialty referral example from before,</a> <a data-t="715">the way that you would generate a benchmark for that is basically taking</a> <a data-t="718">your prompts and your clinical notes about a patient, showing them directly to</a> <a data-t="722">a clinician, and then asking, would you place the referral to the specialist for</a> <a data-t="726">this patient, yes or no? If you do that for a hundred patients, you've now</a> <a data-t="730">generated a data set that the model never saw during training because it</a> <a data-t="733">lives within your walled garden of your databasing of your organization, and</a> <a data-t="737">then you can then use that benchmark to evaluate many different LLMs on that</a> <a data-t="742">task, whether they already exist or if they are released in the future.</a></p>

<p><a data-t="742">So what</a> <a data-t="748">we've done in our organization is to basically do this for many different</a> <a data-t="751">tasks that we have identified as high-value, and then bundled them all</a> <a data-t="756">together in a custom Python evaluation harness called Medhelm, or medical</a> <a data-t="761">holistic evaluation of language models, that is actually quite similar under the</a> <a data-t="765">hood to some of the other evaluation frameworks that have been discussed in</a> <a data-t="768">this session. And in fact, we may end up porting it over to something like</a> <a data-t="772">Inspect in the future.</a></p>

<p><a data-t="772">All right, finally, this brings us to our third key</a> <a data-t="778">difference between monitoring LLM performance and monitoring the</a> <a data-t="781">performance of other kinds of statistical models, and this one is the</a> <a data-t="784">hardest. At the end of the day, no matter how big or expansive your</a> <a data-t="792">suite of benchmarks is, you just can't evaluate an LLM on every single task</a> <a data-t="796">that you could potentially apply it to within your organization. It's not</a> <a data-t="799">possible, and even if it were, it'd be prohibitively expensive to do. This</a> <a data-t="804">is because LLM outputs are just so much more flexible and expressive than other</a> <a data-t="808">kinds of models that are trained for one or a small number of specific purposes.</a> <a data-t="812">They can take pretty much anything as input, and they can produce pretty</a> <a data-t="816">much anything as output.</a></p>

<p><a data-t="816">So what do you do? Our approach is to identify important</a> <a data-t="823">and known failure modes across many of your different LLM deployments and try</a> <a data-t="827">to focus on those. So you basically identify things that you don't want the</a> <a data-t="831">LLM to do, and you monitor those specifically. This is helpful not just</a> <a data-t="836">for monitoring purposes, but it also is kind of a step into a process called</a> <a data-t="840">guardrailing your model, which basically means trying to intercept those failure</a> <a data-t="844">modes before they occur.</a></p>

<h3>Monitoring hallucinations with fact decomposition</h3>

<p><a data-t="844">So for example, at our organization, something that we're</a> <a data-t="850">really worried about is this issue of LLM hallucinations. Probably many of you</a> <a data-t="854">who work with LLMs are concerned about these as well. In our context, an LLM</a> <a data-t="858">hallucination just means that the model makes a claim about a patient that is</a> <a data-t="863">not substantiated or supported by any of the information present in that</a> <a data-t="868">patient's chart. So what we do to monitor this is basically we run automated</a> <a href="/software/quarto/">Quarto</a><a data-t="873"> reports that basically conduct a Python analysis using an algorithm</a> <a data-t="878">called fact decomposition, and this estimates the hallucination rate across</a> <a data-t="882">our chatter deployments for us.</a></p>

<p><a data-t="882">So how does fact decomposition work? Bear with</a> <a data-t="887">me, it's like an algorithmic talk. You start with the output text</a> <a data-t="894">that an LLM generates, and then you use either natural language processing or</a> <a data-t="898">another LLM to break it into the individual claims that it contains. So</a> <a data-t="904">for example, if the claim or if the output from the LLM says this patient</a> <a data-t="910">came to the neurology clinic to have their headache evaluated, the individual</a> <a data-t="914">claims would be that the patient has a headache and that they went to the</a> <a data-t="917">neurology clinic, and maybe also a third one that's like that their evaluation of</a> <a data-t="920">the neurology clinic was about their headache. Once you have these individual</a> <a data-t="924">claims, you can then use a powerful reasoning model or a smaller fine-tuned</a> <a data-t="928">language model to cross-reference all of the individual claims with all of the</a> <a data-t="933">clinical notes within the relevant time period of that patient's chart.</a> <a data-t="937">This basically allows you then to flag individual claims that are not supported</a> <a data-t="942">by any of the evidence present in the patient's record, and using simple</a> <a data-t="947">division you can then compute, like estimate a rate at which like how many</a> <a data-t="951">claims or what proportion of claims are supported versus not supported.</a></p>

<p><a data-t="951">So as an</a> <a data-t="956">example, this is a plot that I pulled or that I made in plot 9 that I pulled</a> <a data-t="961">from our most recent partial report that ran for the month of August, and</a> <a data-t="964">basically what we're doing is we're estimating the hallucination rates</a> <a data-t="967">across our different deployments among three of the different models that we</a> <a data-t="971">route to within the chatter infrastructure. What you can see is that</a> <a data-t="974">one of the models that is becoming a bit dated at this point, GPT-40 mini, was</a> <a data-t="979">hallucinating at a much much higher rate than the other models that we were using,</a> <a data-t="982">so this resulted in the recommendation basically to deprecate that model and</a> <a data-t="987">switch to one that was more reliable.</a></p>
