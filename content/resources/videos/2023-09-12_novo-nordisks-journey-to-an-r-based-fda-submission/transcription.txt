<p><a data-t="1137">So when we do a risk assessment,</a> <a data-t="1139">we lean heavily on the R Validation Hub's</a> <a data-t="1142">recommendations on how to categorize.</a> <a data-t="1145">So the main points of categorization is the type of use,</a> <a data-t="1148">the maintenance, the popularity, and so on.</a> <a data-t="1152">So at the end of the day,</a> <a data-t="1153">this is just a human risk assessment,</a> <a data-t="1155">and the way we prompt this assessment to get made</a> <a data-t="1159">is by a Shiny app.</a></p>

<h3>Internal R packages</h3>

<p><a data-t="1233">So we now have a GXP environment</a> <a data-t="1236">and we have a strategy for packages,</a> <a data-t="1239">but we still do not have R code</a> <a data-t="1241">for producing tables, figures, and listings.</a> <a data-t="1243">We do not have batch execution and logging capabilities</a> <a data-t="1246">in R, what about those?</a></p>

<p><a data-t="1249">This is also handled by the packages,</a> <a data-t="1253">our internal packages,</a> <a data-t="1254">and these internal packages,</a> <a data-t="1255">they started as a single package,</a> <a data-t="1257">one package to rule them all in 2018,</a> <a data-t="1261">and this was developed on a local laptop,</a> <a data-t="1264">and it was simply a gathering</a> <a data-t="1265">of all the usual functions that have been made.</a></p>

<p><a data-t="1269">In 2020, we introduced the nnBiostat package</a> <a data-t="1274">that was simply defined as the accepted packages.</a> <a data-t="1279">So users would write library in nnBiostat</a> <a data-t="1281">and get the most useful packages.</a></p>

<p><a data-t="1286">In 2021, we realized that nnR had become too big</a> <a data-t="1291">and it was split into packages related to specific tasks.</a> <a data-t="1296">So nnR then became just a simple umbrella</a> <a data-t="1299">of all of these packages,</a> <a data-t="1300">like you know from </a><a href="/software/tidyverse/">Tidyverse</a><a data-t="1300">.</a></p>

<p><a data-t="1304">So the most important of our internal packages</a> <a data-t="1307">is nnAccess, that is for getting data</a> <a data-t="1308">without worrying about paths or data formats.</a> <a data-t="1311">It's nnPlot for creating NovoStyle plots.</a> <a data-t="1315">It's nnTable, which defines the grammar of tables</a> <a data-t="1319">for laying out tables and creating text-based output.</a> <a data-t="1323">So we wanted to mimic what we already did in SAS.</a> <a data-t="1327">It can also produce HTML outputs.</a> <a data-t="1330">We also have nnExport for exporting table figures</a> <a data-t="1334">and lists that fit into our production pipeline.</a> <a data-t="1338">And we have nnLog for batch execution and logging.</a> <a data-t="1342">Here we actually use niraspin to create nice-looking logs.</a></p>

<p><a data-t="1348">So, and although these packages,</a> <a data-t="1350">they fit together in a complicated network,</a> <a data-t="1352">each package is just like in the real world,</a> <a data-t="1355">it has its own repo.</a> <a data-t="1357">It is managed in an open-source way internally.</a> <a data-t="1361">And we have version numbers, a maintainer group,</a> <a data-t="1364">we have pipelines, and we have boards</a> <a data-t="1367">for managing bugs, features, ideas, and much more.</a></p>

<p><a data-t="1373">So we aimed to follow a common</a> <a data-t="1376">and good software principles of modularity,</a> <a data-t="1379">and we tried to build up functionality like Lego bricks.</a> <a data-t="1383">So we tried to segregate the responsibility of the packages</a> <a data-t="1387">and define appropriate extraction levels.</a> <a data-t="1390">So at the bottom here,</a> <a data-t="1391">you see the packages that are close to the system.</a> <a data-t="1394">They are system-dependent, if you will.</a> <a data-t="1397">And on top, you see the packages</a> <a data-t="1399">that are close to the task at hand.</a></p>

<p><a data-t="1402">At the top, users shouldn't worry</a> <a data-t="1404">about how the data is stored,</a> <a data-t="1406">where is it stored, and so on.</a> <a data-t="1409">They should just concentrate on the task.</a></p>

<p><a data-t="1412">So for example, a programmer wishes to use nntfl</a> <a data-t="1417">to make a mean plot that will call nnAccess</a> <a data-t="1421">to fetch ADAM data through a connection set up</a> <a data-t="1423">by nnRemote.</a> <a data-t="1425">And after the plot has been made,</a> <a data-t="1426">nnExport will take care of exporting the data</a> <a data-t="1429">to an appropriate data format</a> <a data-t="1431">and associated files that we need.</a></p>

<p><a data-t="1435">So this has the benefit</a> <a data-t="1436">that we can change underlying architectures in the system</a> <a data-t="1441">and simply just do small changes</a> <a data-t="1444">in the lower-level packages, if you will,</a> <a data-t="1448">and the users won't see a difference.</a> <a data-t="1450">So this is also the reason</a> <a data-t="1451">that we could inject a caching system into the system.</a></p>

<h3>Tool chain and code quality</h3>

<p><a data-t="1458">So let's talk about the tool chain that we use in Novo.</a> <a data-t="1462">So we use git for version control</a> <a data-t="1465">and Azure Pipelines for executing code upon code changes.</a> <a data-t="1471">We use useless for the description file and the news file.</a> <a data-t="1475">We use package down for generating a website</a> <a data-t="1480">of documentation,</a> <a data-t="1481">and we use our oxygen to write the documentation.</a></p>

<p><a data-t="1486">We use lifecycle to convey the stability</a> <a data-t="1489">or the lifecycle of a function within the packages.</a> <a data-t="1494">And we use test.uncover to test the packages.</a> <a data-t="1498">We also use our markdown</a> <a data-t="1499">for writing longer format documentation</a> <a data-t="1502">in the form of vignettes.</a> <a data-t="1504">And we use </a><a href="/software/devtools/">DevTools</a><a data-t="1504"> to do the normal system,</a> <a data-t="1508">sorry, the normal package development.</a></p>

<p><a data-t="1511">So upon a code change,</a> <a data-t="1514">we will test again the package in a matrix way.</a> <a data-t="1519">So we test against all our libraries,</a> <a data-t="1521">all our versions of R</a> <a data-t="1523">and across all of our system environments.</a></p>

<p><a data-t="1529">So we know that if, for example,</a> <a data-t="1531">an upcoming change in development to the system</a> <a data-t="1534">will break something in our packages.</a> <a data-t="1537">We then build the package and then we release it.</a> <a data-t="1540">So in the process of releasing,</a> <a data-t="1542">we are updating the package down website</a> <a data-t="1545">and we ship it to the internal repo in the package manager.</a></p>

<p><a data-t="1550">So we realized some time ago,</a> <a data-t="1553">but we implemented it this year</a> <a data-t="1556">that we need the ability to deprecate our versions.</a> <a data-t="1560">So say we no longer want to support</a> <a data-t="1563">the oldest version of R we have and stop,</a> <a data-t="1566">then we have made version specific repos</a> <a data-t="1572">so we can stop updating that.</a> <a data-t="1575">This also allows for hotfixes if system changes are needed.</a></p>

<p><a data-t="1581">So we try to ensure a high level of code quality</a> <a data-t="1584">by enforcing a main branch policy.</a> <a data-t="1587">Nobody can change the main branch directly.</a> <a data-t="1590">Only pull requests to the main branch are accepted.</a> <a data-t="1594">The pipeline needs to run with success and no errors.</a> <a data-t="1598">A feature or bot needs to be linked to the pull request</a> <a data-t="1602">so we know why we have to change.</a> <a data-t="1604">And we need at least one maintainer to approve</a> <a data-t="1608">to ensure a code review.</a></p>
