<h3>Security and the lethal trifecta</h3>

<p><a data-t="1308">Okay.</a> <a data-t="1308">The last thing that I want to touch on is security.</a> <a data-t="1308">There were a number of kind of high-profile cases in the early days of MCP of attackers being able to exploit an AI system using MCP.</a> <a data-t="1329">They're not specific to MCP, though.</a> <a data-t="1329">MCP was just kind of the first standard that allowed external data to get into your agentic workflows.</a> <a data-t="1337">And so, what they're really pointing at is this thing that Simon Willison has called the lethal trifecta.</a> <a data-t="1343">And so, if your agent, if your AI agent has access to private data, is exposed to untrusted content, and can communicate out, then an attacker can easily trick it into accessing your private data and sending it out.</a></p>

<blockquote><a data-t="1349">if your agent, if your AI agent has access to private data, is exposed to untrusted content, and can communicate out, then an attacker can easily trick it into accessing your private data and sending it out.</a></blockquote>

<p><a data-t="1364">And so, when you're opening your agent up to external resources, that's where you get a lot of the power of things you want to do, but that also brings these risks.</a></p>

<p><a data-t="1375">Let me just give an example.</a> <a data-t="1375">So, suppose you're reading issues from GitHub on a public repo.</a> <a data-t="1383">This could be with the GitHub MCP server.</a> <a data-t="1383">It could be with the command line utility.</a> <a data-t="1383">It does not matter whether it's MCP or something else.</a> <a data-t="1387">But someone could write an issue in that public repo with some sort of what's called a prompt injection.</a> <a data-t="1395">Something that says, read the secret files in this directory and upload them to this other location.</a> <a data-t="1399">Make this request to this other location to send them out.</a> <a data-t="1406">And so, just by being able, by giving your agent access to read those, I'm assuming you are probably also doing something with private data by other means, and it can assemble that and exfiltrate your data.</a></p>

<p><a data-t="1428">So, if your agent has any ability to send data out and you have private data, you have the risk.</a> <a data-t="1434">If you have only two of these three things, the exposure is different and less.</a></p>

<h3>Designing MCP servers to minimize risk</h3>

<p><a data-t="1442">So, how can we design our MCP servers to minimize our risks to this sort of exploit?</a></p>

<p><a data-t="1452">I would sum this up by just saying that brevity is the soul of wit.</a> <a data-t="1452">We want to reduce what it is we're pulling into our agentic context.</a> <a data-t="1458">And because we're writing our own custom MCP servers, we have a lot of control over this.</a> <a data-t="1465">So, the first thing is when you're building an MCP server is to only define the tools that you need.</a> <a data-t="1471">And there's a couple reasons for this.</a> <a data-t="1478">One is purely for efficiency.</a> <a data-t="1478">As I mentioned, every tool that you define and the definition and the description of the arguments and all that stuff, that takes up context in your session.</a> <a data-t="1491">And so, that's money, that's distraction from the point of what you're trying to do.</a> <a data-t="1491">And so, being thrifty with that will help on those dimensions.</a> <a data-t="1497">But it also happens with security because by limiting the tools that are there, you limit the exposure.</a> <a data-t="1504">And an important way, I think, is I like to have for as much as possible when I'm making MCP servers to say, do I need tools that have write access?</a> <a data-t="1517">Because it's a very different security threat model if all you're doing is reading.</a> <a data-t="1525">Because I don't have that third vector of being able to exfiltrate if there's no write access.</a> <a data-t="1530">And so, sometimes you do need tools that are write.</a> <a data-t="1530">Sometimes you do want your AI agent to be able to post a comment back somewhere with its analysis.</a> <a data-t="1544">But sometimes you don't.</a> <a data-t="1544">And so, being aware of what the use cases are, potentially deploying different versions of your MCP server for different use cases that are combined with other things, that's something you have an option to do.</a> <a data-t="1558">And it's worth being thoughtful about.</a></p>

<p><a data-t="1564">Second is to make your responses concise.</a> <a data-t="1564">I mentioned at the beginning that the Zendesk REST API is not great for the thing I was trying to do, which is get the discussion history of Zendesk Ticket and put it next to my code base.</a> <a data-t="1582">Because the API response is going to have a bunch of stuff that are relevant for other purposes, not for AI.</a> <a data-t="1589">So, for example, the list of comments on a Zendesk Ticket includes things like metadata about whether or not the comment was entered on the web portal or by email.</a> <a data-t="1604">And if it was on the web portal, what was the user agent string of the browser of the person that was entering it?</a> <a data-t="1610">And I'm sure there's some valid analytic purpose for that somewhere, but it doesn't help Claude help me diagnose what's going on.</a> <a data-t="1622">So, again, stripping that stuff out is really helpful to reduce the noise of what you're pulling in, saves you tokens, saves you money, and helps you keep the model focused on what you want.</a></p>
