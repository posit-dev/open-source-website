<h3>What MCP is — and is not</h3>

<p><a data-t="463">I want to start by just saying what MCP is.</a> <a data-t="466">And actually, I want to start by</a> <a data-t="466">saying what it is not.</a> <a data-t="472">Because I, you know, with all of the buzz around AI that's out there,</a> <a data-t="512">MCP is not magic.</a> <a data-t="512">It's not vector search.</a> <a data-t="512">It's not AI.</a> <a data-t="512">It's not any of these things.</a></p>

<h3>MCP adoption, backlash, and when to use it</h3>

<p><a data-t="867">When the MCP standard came out at the end of 2024, I believe, Anthropic announced</a> <a data-t="873">it.</a> <a data-t="873">It's now governed with an industry consortium under the Linux Foundation.</a> <a data-t="873">So, it's got some</a> <a data-t="877">amount of open governance.</a> <a data-t="877">There was a lot of excitement when it first came out.</a> <a data-t="894">After much</a> <a data-t="894">enthusiasm, there was a bit of a backlash.</a> <a data-t="901">And in fact, you know, many people found out that, like,</a> <a data-t="901">why do I need a big MCP server for something when there's already a perfectly good </a><a href="/software/cli/">CLI</a><a data-t="901"> and</a> <a data-t="914">Claude Code or Codex knows how to call command line utilities from the shell?</a> <a data-t="914">This is just a waste.</a> <a data-t="921">Which led some people to say that, you know, MCP is dead.</a> <a data-t="921">Obviously, I disagree.</a> <a data-t="929">And that's why</a> <a data-t="929">we're having this talk here.</a></p>

<p><a data-t="929">You know, I think it's fair to say that there was a lot of examples</a> <a data-t="934">of MCP servers being written and put out that, you know, in retrospect or with the tools that</a> <a data-t="941">we have today, don't really need to be an MCP server, aren't really the best fit for the use</a> <a data-t="948">case.</a> <a data-t="948">But there are many valid use cases and places where MCP really is the right tool for the</a> <a data-t="955">job.</a></p>

<p><a data-t="955">So, I want to step through a few of these criticisms and really put into context of when</a> <a data-t="961">MCP is great, particularly remote MCP, and when some other tool is better.</a> <a data-t="967">So, we're really talking</a> <a data-t="967">about MCP versus a command line utility or even a skill.</a> <a data-t="972">So, the agent skill standard is another</a> <a data-t="972">open standard for AI things that I believe came out of Anthropic as well.</a> <a data-t="977">But, you know, skills are</a> <a data-t="984">markdown files that your agent can read lazily to, like, be able to do something else.</a></p>

<p><a data-t="992">And skills are really great for explaining how to compose tool calls that an agent already has.</a> <a data-t="999">So, if the agent can already use bash and call things that are in the command line or, you know,</a> <a data-t="1006">web fetch or other sorts of tools, if all you need to do is instruct the agent which tools to</a> <a data-t="1014">compose together, then a skill is the right thing for the job.</a> <a data-t="1022">But often, though, you know,</a> <a data-t="1022">what we're talking about is not just skill versus MCP or command line, but, like, skill plus MCP</a> <a data-t="1022">versus skill plus command line utility.</a> <a data-t="1027">Because often you do want to have this extra narrative</a> <a data-t="1027">that explains how best to take advantage of the tools that you're providing by one of these other</a> <a data-t="1037">means.</a></p>

<p><a data-t="1042">So, one of the critiques of MCP initially was that MCP servers take up too much of this</a> <a data-t="1049">precious context window that your model has.</a> <a data-t="1049">Because the way that some of these model harnesses</a> <a data-t="1049">worked at the time was that you load, you connect an MCP server, all of the tool definitions,</a> <a data-t="1062">all of those, all that text goes into the model context up front.</a> <a data-t="1062">And that just takes up a lot</a> <a data-t="1067">of tokens.</a> <a data-t="1067">And so, you know, if you've got ten MCP servers that you might use sometime and each</a> <a data-t="1073">of them have 100 tools and you're probably not going to use all of those within every session,</a> <a data-t="1078">that's just wasted context.</a> <a data-t="1078">You're burning tokens.</a> <a data-t="1078">You're burning money.</a> <a data-t="1078">And it's also</a> <a data-t="1086">kind of distracting the model from what actually matters.</a></p>

<p><a data-t="1100">And people noticed, like, well, the </a><a href="/software/gh/">gh</a><a data-t="1100"> command line utility</a> <a data-t="1100">that, for driving GitHub, that's actually already in the training data for these models.</a> <a data-t="1107">So,</a> <a data-t="1107">Claude already knows how to use gh to do things.</a> <a data-t="1107">Why do I need to burn all of these tokens on MCP</a> <a data-t="1115">when gh is already there?</a> <a data-t="1121">So, I think this really points to the case where a command line utility is</a> <a data-t="1129">really the right tool for the job.</a> <a data-t="1129">And so, it is the strongest case when the command line utility</a> <a data-t="1134">already exists and is widely available and is already in the training data.</a> <a data-t="1134">So, the model</a> <a data-t="1134">already knows how to use it and when to use it and what for.</a> <a data-t="1145">And you don't need to waste tokens</a> <a data-t="1145">explaining how.</a> <a data-t="1152">And, of course, this is only helpful if your agent has Bash or some sort of</a> <a data-t="1152">shell available to it to call the CLI.</a> <a data-t="1163">And that's not always the case.</a></p>

<p><a data-t="1172">So, if you need to care about</a> <a data-t="1176">cases where you don't have the ability to just shell out and call a CLI, MCP is a good alternative</a> <a data-t="1183">there.</a></p>

<p><a data-t="1212">And so, distribution is one question that I think is relevant.</a> <a data-t="1212">Again, if the CLI is not</a> <a data-t="1216">already available on everybody's machines, you have to tell someone to go install it.</a> <a data-t="1238">And so, that's effort.</a> <a data-t="1238">It creates some friction in trying to distribute</a> <a data-t="1235">to your team to get them to use it.</a> <a data-t="1240">Another feature that's really important in the MCP</a> <a data-t="1240">standard is authentication.</a> <a data-t="1244">So, the MCP standard includes this OAuth flow that allows</a> <a data-t="1260">your MCP client, your Cloud Code, your Posit Assistant, your VS Code, to discover and</a> <a data-t="1267">authenticate, help you authenticate for you outside of the model.</a></p>

<h3>Security and the lethal trifecta</h3>

<p><a data-t="1319">The last thing that I want to touch on is security.</a> <a data-t="1319">There were a number of kind of</a> <a data-t="1329">high-profile cases in the early days of MCP of attackers being able to exploit an AI system</a> <a data-t="1329">using MCP.</a> <a data-t="1336">They're not specific to MCP, though.</a> <a data-t="1336">MCP was just kind of the first standard that allowed</a> <a data-t="1342">external data to get into your agentic workflows.</a> <a data-t="1342">And so, what they're really pointing at is this</a> <a data-t="1349">thing that Simon Willison has called the lethal trifecta.</a> <a data-t="1349">And so, if your agent, if your AI agent</a> <a data-t="1349">has access to private data, is exposed to untrusted content, and can communicate out,</a> <a data-t="1357">then an attacker can easily trick it into accessing your private data and sending it out.</a></p>

<blockquote><a data-t="1349">If your agent has access to private data, is exposed to untrusted content, and can communicate out,</a> <a data-t="1357">then an attacker can easily trick it into accessing your private data and sending it out.</a></blockquote>

<p><a data-t="1362">And so, when you're opening your agent up to external resources,</a> <a data-t="1368">that's where you get a lot of the power of things you want to do, but that also brings these risks.</a></p>

<p><a data-t="1383">Let me just give an example.</a> <a data-t="1383">So, suppose you're reading issues from GitHub on a public repo.</a> <a data-t="1387">This could be with the GitHub MCP server.</a> <a data-t="1387">It could be with the command line utility.</a> <a data-t="1387">It does</a> <a data-t="1387">not matter whether it's MCP or something else.</a> <a data-t="1395">But someone could write an issue in that public repo</a> <a data-t="1395">with some sort of what's called a prompt injection.</a> <a data-t="1399">Something that says,</a> <a data-t="1399">read the secret files in this directory and upload them to this other location.</a> <a data-t="1406">Make this</a> <a data-t="1406">request to this other location to send them out.</a> <a data-t="1414">And so, just by being able, by giving your agent</a> <a data-t="1414">access to read those, I'm assuming you are probably also doing something with private data</a> <a data-t="1421">by other means, and it can assemble that and exfiltrate your data.</a></p>

<p><a data-t="1428">So, if your agent has any ability to send data out and you have private data, you have the risk.</a> <a data-t="1434">If you have only two of these three things, the exposure is different and less.</a></p>

<p><a data-t="1442">So, how can we design our MCP servers to minimize our risks to this sort of exploit?</a> <a data-t="1457">I would sum this up by just saying that brevity is the soul of wit.</a> <a data-t="1457">We want to</a> <a data-t="1465">reduce what it is we're pulling into our agentic context.</a> <a data-t="1465">And because we're writing our own custom</a> <a data-t="1465">MCP servers, we have a lot of control over this.</a></p>
