<h3>Introducing the 3rd edition</h3>

<p><a data-t="54">So the big news with this release of testthat, this upcoming release, testthat 3.0, is we're going to introduce the idea of this 3rd edition.</a> <a data-t="63">And I should say anything you're going to hear about today is also explained in more detail in vignettes on the testthat website, so if you want to learn more about anything I say today, feel free to take a look at those vignettes, and if they don't explain, they don't help you understand what's going on, please file an issue so we can learn better.</a></p>

<p><a data-t="83">So the basic idea of the addition is that we want to make breaking changes to testthat.</a> <a data-t="88">Testthat's like 10 years old or something, and there's a bunch of things in the package that we now regret.</a> <a data-t="96">But testthat's kind of a victim of its own popularity.</a> <a data-t="100">There's something like 4,000 or 5,000 packages on CRAN that use testthat, and many of them are not actively developed.</a> <a data-t="107">So there's no way we can change testthat without breaking a bunch of packages, and many of these packages, since they wouldn't be maintained, they'd just end up off CRAN because people wouldn't have the energy to fix them.</a></p>

<p><a data-t="122">So the idea of an addition is that this is something you have to deliberately opt into.</a> <a data-t="128">So if you want to use many of the new features or all of the new features of testthat I talk about today, you have to deliberately choose to use a 3rd edition of testthat.</a> <a data-t="138">And to sort of do that, you basically have to add a line in your description file, </a><a href="/software/config/">config</a><a data-t="138"> slash testthat slash addition.</a> <a data-t="144">So if you don't do this, you'll continue to use the second edition, that's the existing behavior of testthat.</a> <a data-t="149">If you do this, you'll get, if you do change this, you'll get a bunch of new features and a bunch of things, which I'll explain shortly, which have gone away.</a></p>

<p><a data-t="158">So the kind of idea is that it should take hopefully, you know, less than 30 minutes to convert a package to use the 3rd edition.</a> <a data-t="168">You know, it's a little bit of work, hopefully not too much work, but it just generally gets you up to date with all of our best current best practices.</a> <a data-t="176">And I should say, if this kind of idea of this addition idea is successful, it's something we're likely to try out in other packages, a way of allowing existing code to continue working while giving you the choice to opt into a new set of behaviors.</a></p>

<p><a data-t="194">So additions will always be coupled with a major version.</a> <a data-t="197">So that means testthat2 and everything else before this counts as the 2nd edition, testthat3.0 can use the 2nd edition, that's the default behavior, or you can opt into using the 3rd edition.</a> <a data-t="210">And if one day, you know, many, probably multiple years down the line, we decide to introduce a 4th edition, then that would be tied to testthat4.0.</a></p>

<h3>Snapshot testing</h3>

<p><a data-t="749">Okay, so that's waldo.</a> <a data-t="751">I think that's like kind of the number one feature, like, again, I have found it like so useful when debugging tests myself to have that much, much, much clearer display.</a> <a data-t="764">The next big feature I want to talk about is snapshot testing.</a> <a data-t="768">Again, this comes with a vignette, so if you want to learn more about it, you can read the vignette.</a> <a data-t="772">If the vignette doesn't make sense, please file an issue so we can make it better.</a></p>

<p><a data-t="777">But the basic idea is this is a new type of testing.</a> <a data-t="783">So normally in unit tests, you describe the expected output using code.</a> <a data-t="790">And in the vast majority of cases, this is a really, really good idea because it allows you to kind of describe what you expect.</a> <a data-t="797">And in some sense, the tests help document, because the tests are code and code is a means of communication.</a> <a data-t="804">They kind of help describe the expected behavior of the functions as well.</a> <a data-t="809">But sometimes describing the expected output is just like really annoying, like if it contains a bunch of special characters, like quotes or backslashes, you have to spend a bunch of time like carefully escaping them.</a> <a data-t="821">And then when something goes wrong, it's hard to see exactly, like you've got to unescape them in your head, and it's just a pain.</a> <a data-t="827">Or maybe it's very large, like maybe you want to check an entire HTML page or multiple paragraphs of text, as you expect.</a> <a data-t="836">Or maybe it's not even something that you can easily describe with text.</a> <a data-t="840">It's an image.</a> <a data-t="842">Or something else.</a></p>

<p><a data-t="843">So the idea of a snapshot or golden test, which idea used in other programming languages and other testing packages, and test that inspiration draws primarily from Jest, which is a JavaScript testing package that Joe Chang shared his experiences with me a bunch and persuaded me that this was something really useful.</a> <a data-t="872">But so the snapshot test, the key idea is that instead of recording the results inline in the test itself, they're stored in a separate file.</a> <a data-t="881">And testthat provides a bunch of tools for looking after that, for managing that file.</a> <a data-t="887">So it will create it automatically the first time you run it, and then it gives you tools to update it when you decide there really has to be a change.</a> <a data-t="895">And if you've used verify output or expect known output, which we've never really advertised because we've never really been particularly happy with them, the snapshot tests basically</a></p>

<h3>Snapshot file format</h3>

<h3>Parallel tests</h3>

<p><a data-t="1542">Next, I wanted to talk briefly about parallel tests.</a> <a data-t="1546">This is still work in progress by Gabor Chadi.</a> <a data-t="1551">And again, you're going to have to activate this specifically for your package again by</a> <a data-t="1555">putting another line in your description, config, test that parallel true.</a> <a data-t="1560">But the payoff for this is pretty big.</a> <a data-t="1562">It's going to run your tests on multiple processes.</a> <a data-t="1568">So if you have long running tests, this is going to make a big improvement to the total</a> <a data-t="1574">running time of your tests.</a></p>

<p><a data-t="1655">So we're still thinking about tools to kind of ensure that if that happens to you, we've</a> <a data-t="1659">got some mode debugging mode you can switch on to get more insight.</a> <a data-t="1664">And then also, if you have used like global setup or teardown, for example, like you set</a> <a data-t="1668">up a database or some CSV file for all of your tests, you're going to need to think</a> <a data-t="1675">that through in a little bit more detail because those setup and teardown files are</a> <a data-t="1680">now run by multiple processes.</a> <a data-t="1684">So there's going to be a little bit of work to convert your tests to use Parallel.</a> <a data-t="1688">We're still working on this.</a> <a data-t="1689">You know, there's a vignette if you want to learn more and want to try it out.</a> <a data-t="1692">But we're hopeful that this will make a big impact if you've got long running tests.</a></p>
