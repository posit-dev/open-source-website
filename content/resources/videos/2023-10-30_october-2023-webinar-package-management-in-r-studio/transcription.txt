<h3>Package dependency conflicts</h3>

<p><a data-t="1837">Okay, so now that we've covered packages, libraries, and repositories,</a> <a data-t="1840">let's talk about the not-so-fun stuff.</a> <a data-t="1843">And that is package dependency conflicts,</a> <a data-t="1846">or basically what happens when things go wrong.</a> <a data-t="1849">So let me run through a scenario with you.</a> <a data-t="1852">I'm going to pick a random date. This is completely arbitrary.</a> <a data-t="1855">We'll say January 1, 2020.</a> <a data-t="1858">You open up R and RStudio, and you install a package.</a> <a data-t="1861">We'll focus on the tbl package, which some of you may be familiar with.</a></p>

<p><a data-t="1865">So we go and install .packages, the tbl package.</a> <a data-t="1869">It is very common in R, and also in Python,</a> <a data-t="1872">for packages to depend on other packages.</a> <a data-t="1876">So by installing the tbl package, it actually, by default,</a> <a data-t="1880">will install three dependencies, the </a><a href="/software/rlang/">rlang</a><a data-t="1880">, cli, and cran packages.</a></p>

<p><a data-t="1886">Now, again, on this date, we installed tbl and all those dependencies,</a> <a data-t="1889">so they're all being installed at the exact same time.</a> <a data-t="1892">And there's actually a cool thing that CRAN does.</a> <a data-t="1895">So again, that big repository of R packages.</a> <a data-t="1898">CRAN always tests to ensure that the latest packages</a> <a data-t="1901">always work together.</a> <a data-t="1904">So if you install these packages on the exact same date,</a> <a data-t="1908">all the packages and the versions and dependencies,</a> <a data-t="1911">they should all work nicely together. You shouldn't get any conflicts.</a></p>

<p><a data-t="1914">But let's fast forward a month.</a> <a data-t="1917">I'm just taking some arbitrary time.</a> <a data-t="1920">And you go back into that same R environment where you install tbl.</a> <a data-t="1923">And you now install another package,</a> <a data-t="1926">and we'll focus on the packagedown package.</a> <a data-t="1929">So you install packagedown. It turns out packagedown</a> <a data-t="1932">actually has the same three dependencies,</a> <a data-t="1935">rlang, </a><a href="/software/cli/">cli</a><a data-t="1935">, and cran.</a> <a data-t="1938">But because this is being installed a month later,</a> <a data-t="1941">it turns out there's actually some new versions of these various dependencies,</a> <a data-t="1944">which is why they're kind of shaded in this darker gray color.</a> <a data-t="1947">So by installing packagedown on February 1st,</a> <a data-t="1950">it'll automatically update the rlang, cli, and cran packages.</a> <a data-t="1953">But what it will not do is update the tbl package itself.</a></p>

<p><a data-t="1956">And now you're in a bit of a broken state</a> <a data-t="1959">because you have an old version of tbl</a> <a data-t="1962">that's trying to use new versions of its dependencies,</a> <a data-t="1965">and you may run into some issues where functions aren't behaving as expected.</a> <a data-t="1968">So how do we get around this?</a></p>

<h3>Freezing a repository</h3>

<p><a data-t="1971">Well, I mentioned before that CRAN tests to ensure</a> <a data-t="1974">that the latest packages always work together.</a> <a data-t="1977">So because of that, it's very common for data science teams</a> <a data-t="1980">to do something what's known as freezing a repository</a> <a data-t="1983">to a set date.</a> <a data-t="1986">So let me explain how this works.</a></p>

<p><a data-t="1989">So again, we have two dates right here, and we have January 1st, 2020.</a> <a data-t="1992">And let's say that you as the user or your administrator</a> <a data-t="1995">decides to freeze your repository</a> <a data-t="1998">to this date, February 1st.</a> <a data-t="2001">You install tbl, things go great, and then you fast forward</a> <a data-t="2004">to February 1st. But even though it's February 1st,</a> <a data-t="2007">your repository is still frozen to January 1st.</a> <a data-t="2010">So you go to install packagedown in February,</a> <a data-t="2013">but it still installs it as if it's January 1st.</a> <a data-t="2016">So no matter when you installed any subsequent packages,</a> <a data-t="2019">they're all being installed as if it's the same time.</a> <a data-t="2022">So all these packages, again, should work together</a> <a data-t="2025">because that's the added service that CRAN provides.</a></p>

<h3>Package management strategies</h3>

<p><a data-t="2028">Okay, now that we've talked about a bunch of different things,</a> <a data-t="2031">you might have some questions kind of circulating in your head</a> <a data-t="2034">as you start to devise your own package management strategy.</a> <a data-t="2037">You know, things like who is going to be responsible</a> <a data-t="2040">for reproducing the environment?</a> <a data-t="2043">Is that going to be up to the data scientists, the users,</a> <a data-t="2046">or is it going to be up to my system administrators?</a> <a data-t="2049">Also, how open is the environment? Can a user</a> <a data-t="2052">install a new package, or are they going to be locked down to a specific</a> <a data-t="2055">version? Should we be using these shared</a> <a data-t="2058">system libraries or just specific user libraries?</a></p>

<p><a data-t="2061">And really, you have to weigh the pros and cons</a> <a data-t="2064">specific to your team. It's nice to talk to</a> <a data-t="2067">other teams as well and to kind of see what they're doing, but ultimately</a> <a data-t="2070">it's just to find a solution that kind of meets your team's</a> <a data-t="2073">needs. Now having said</a> <a data-t="2076">that, we have worked with a bunch of teams here at Posit</a> <a data-t="2079">where we've seen package management strategies succeed</a> <a data-t="2082">and we've seen some strategies not so succeed.</a></p>

<p><a data-t="2085">And so what you're seeing on this plot right here,</a> <a data-t="2088">we're showing you a few different strategies that we're going to</a> <a data-t="2091">touch upon. On the y-axis, we're looking at package</a> <a data-t="2094">access. So that's asking, can a user</a> <a data-t="2097">install whatever package they want? So is it open,</a> <a data-t="2100">or is it fairly locked down? So they're kind of constrained to specific</a> <a data-t="2103">packages or specific versions. And then</a> <a data-t="2106">on the x-axis, we're looking at who is responsible for</a> <a data-t="2109">reproducing the environment. Is that going to be up to your system</a> <a data-t="2112">administrators, or is it going to be up to the data scientists?</a> <a data-t="2115">We find teams have the most success</a> <a data-t="2118">somewhere along this diagonal. And we're</a> <a data-t="2121">actually going to talk about these three strategies. We're going to start with snapshot,</a> <a data-t="2124">then we'll talk about shared baseline, and then finally a validated</a> <a data-t="2127">strategy. And then we'll just briefly touch</a> <a data-t="2130">upon some of these other strategies where we see things go a little</a> <a data-t="2133">bit haywire.</a></p>

<h3>Snapshot strategy</h3>

<p><a data-t="2133">So let's go ahead and start with</a> <a data-t="2136">snapshot in the top right corner here. For</a> <a data-t="2139">every single one of these strategies, we'll kind of talk about what</a> <a data-t="2142">they are and then some pros and cons of each.</a> <a data-t="2145">So in a snapshot strategy, users are able</a> <a data-t="2148">to freely access and install whatever package</a> <a data-t="2151">they want, but you must be using RStudio</a> <a data-t="2154">projects and that renv package we talked about before.</a> <a data-t="2157">You have to be using that renv lock file.</a></p>

<p><a data-t="2160">So in this scenario, users are going to have the</a> <a data-t="2163">full responsibility to record the dependencies</a> <a data-t="2166">needed for a project. So in a typical workflow,</a> <a data-t="2169">you would create a project, you then write some code,</a> <a data-t="2172">install some packages, write more code, install other packages,</a> <a data-t="2175">and you use that renv package to</a> <a data-t="2178">snapshot your environment, to record what packages you're using.</a> <a data-t="2181">That's going to update that lock file, which you can then use</a> <a data-t="2184">to restore your environment if needed.</a></p>

<p><a data-t="2187">Now the pros for a snapshot is that it definitely gives</a> <a data-t="2190">users access to pretty much any package and any version</a> <a data-t="2193">they want to use. And the</a> <a data-t="2196">second point right here, I put it as a pro, but depending on your</a> <a data-t="2199">team, you may consider it a con. It's really going to</a> <a data-t="2202">require little to no IT or sysadmin involvement.</a> <a data-t="2205">It's really going to be on the shoulders of the users.</a> <a data-t="2208">And that kind of leads me to my major</a> <a data-t="2211">con here, is that if you're brand new to R and now</a> <a data-t="2214">you're being tasked with keeping track of every package you're</a> <a data-t="2217">using and the versions, that can be a slight</a> <a data-t="2220">barrier for those that are brand new to R.</a> <a data-t="2223">Now it's worth noting that if you</a> <a data-t="2226">are running RStudio locally on your personal</a> <a data-t="2229">laptop, we'd certainly recommend that you use</a> <a data-t="2232">this strategy for all of your projects.</a></p>

<h3>Shared baseline strategy</h3>

<p><a data-t="2235">The second strategy we're going to talk about is something known as a shared</a> <a data-t="2241">baseline. And it's just like a side note, this is actually what we use</a> <a data-t="2244">internally here at Posit. In this strategy,</a> <a data-t="2247">all or most of CRAN, so all 19,</a> <a data-t="2250">20,000 packages of CRAN are made available</a> <a data-t="2253">to every single user via that shared</a> <a data-t="2256">system library. But users are</a> <a data-t="2259">still able to freely access and install any</a> <a data-t="2262">package they want, any version they want,</a> <a data-t="2265">and they can install it into their own project and or user</a> <a data-t="2268">library.</a></p>

<p><a data-t="2268">So the reason why</a> <a data-t="2271">we really like this strategy, it's good for both those</a> <a data-t="2274">that are new to R and more advanced users.</a> <a data-t="2277">For those that are new, all these packages are already there available</a> <a data-t="2280">to them. But for the advanced R users, they can still</a> <a data-t="2283">reach out and grab a development version of a package</a> <a data-t="2286">or the latest and greatest. It can also</a> <a data-t="2289">reduce duplicate package installs across users.</a> <a data-t="2292">So I mentioned before that when you use that shared</a> <a data-t="2295">baseline strategy, that prevents every single user</a> <a data-t="2298">installing the same package into their own user library, and especially</a> <a data-t="2301">if you have a large data science team, that can be a bit of a waste of space.</a> <a data-t="2304">I do put this asterisk here, though, because for the most</a> <a data-t="2307">part, packages in R are not very big. They're just a series</a> <a data-t="2310">of text files. So it's not really going to take up</a> <a data-t="2313">that much space on your system, but it can be a way to save</a> <a data-t="2316">up, I know, a couple megabytes.</a></p>

<p><a data-t="2319">Now the cons here, if you're not</a> <a data-t="2322">running Posit within a server environment, then this</a> <a data-t="2325">strategy is not going to be available to you. So it's not going to be available</a> <a data-t="2328">for desktop R users. And then that shared</a> <a data-t="2331">library, it may not include the latest and greatest,</a> <a data-t="2334">and it's ultimately going to be controlled by your system administrators.</a></p>

<h3>Validated strategy</h3>

<p><a data-t="2337">The last strategy we'll talk about is something known as a</a> <a data-t="2343">validated strategy. And this is a very popular strategy,</a> <a data-t="2346">especially amongst our pharmaceutical, our</a> <a data-t="2349">life sciences groups, folks that are going to be</a> <a data-t="2352">submitting things to, say, some regulatory</a> <a data-t="2355">agency like the FDA here in the States.</a> <a data-t="2358">So in a validated strategy, it's going to restrict</a> <a data-t="2361">access to a particular set of packages that</a> <a data-t="2364">your team deems as validated.</a></p>

<p><a data-t="2367">Now I put validated in quotes because</a> <a data-t="2370">a question that I routinely get is, hey, Ryan, is</a> <a data-t="2373">this package considered validated or not? I would love</a> <a data-t="2376">to be able to answer that question. But unfortunately, every single team</a> <a data-t="2379">is unique. And what one team may consider</a> <a data-t="2382">something validated, another team may not. And so</a> <a data-t="2385">every single team kind of has to create their own series</a> <a data-t="2388">of checks to determine if a package</a> <a data-t="2391">is considered validated and use their own judgment.</a></p>

<p><a data-t="2395">Now, also for users of a validated</a> <a data-t="2398">environment, if they want to use a package that's not currently</a> <a data-t="2401">considered validated, then they're kind of out of luck and</a> <a data-t="2404">they have to go through an approval process to hopefully get that</a> <a data-t="2407">package validated in their environment.</a></p>

<p><a data-t="2411">Now, the pros here with a validated strategy and</a> <a data-t="2414">why it's so important for our pharmaceutical groups</a> <a data-t="2417">is that you can confidently recreate the same</a> <a data-t="2420">environment outcome. So if you go to submit something</a> <a data-t="2423">to the FDA, you want to make sure that the results,</a> <a data-t="2426">the same thing, you'll get results today, you'll get the same results</a> <a data-t="2429">a week from now, a year from now, 10 years from now. So you</a> <a data-t="2432">really have to make sure that these analyses do not change at</a> <a data-t="2435">all. And you can trust what's in your environment.</a> <a data-t="2438">You've done your homework. You know every single thing about every</a> <a data-t="2441">single package in your environment. So you can be very confident, be very</a> <a data-t="2444">safe in this validated environment.</a></p>

<blockquote><a data-t="2438">You've done your homework. You know every single thing about every</a> <a data-t="2441">single package in your environment. So you can be very confident, be very</a> <a data-t="2444">safe in this validated environment.</a></blockquote>

<p><a data-t="2444">Now, there's certainly going to be quite a few cons. It will require</a> <a data-t="2450">a lot more IT and sysadmin involvement.</a> <a data-t="2453">Also, maintaining a validated environment is not a trivial</a> <a data-t="2456">task. And I've worked with groups that have dedicated teams</a> <a data-t="2459">just to maintaining a validated environment.</a> <a data-t="2462">And then finally, users can be constrained</a> <a data-t="2465">to select packages. So if there's</a> <a data-t="2468">if they see online or on social media, there's a new package</a> <a data-t="2471">with a function that works perfect for them, they may not</a> <a data-t="2474">have access to it because it's not considered validated.</a></p>

<h3>Strategies to avoid</h3>

<p><a data-t="2478">All right, another flow diagram. We're not going to</a> <a data-t="2481">talk about this one. But again, when I share the slides,</a> <a data-t="2484">you can read through this. And what I'm trying to do is</a> <a data-t="2487">guide users into what package management</a> <a data-t="2490">strategy they should at least consider. So starting</a> <a data-t="2493">here with the user at the very top. So you can see</a> <a data-t="2496">in green here, the three strategies we just talked about, snapshot,</a> <a data-t="2499">shared baseline and validated. But here</a> <a data-t="2502">in red, we also have some strategies which tend not to be</a> <a data-t="2505">so good. And their names kind of</a> <a data-t="2508">kind of tip the hat to what they are.</a></p>

<p><a data-t="2511">So the first strategy is known as Wild West.</a> <a data-t="2514">And so in a Wild West, there's basically</a> <a data-t="2517">no regard for reproducibility. They can install whatever</a> <a data-t="2520">package they want into whatever library they want, whatever version.</a> <a data-t="2523">This is where you run into those package dependency</a> <a data-t="2526">conflicts most frequently. We also</a> <a data-t="2529">have something known as a ticket system. It's very similar</a> <a data-t="2532">to a validated environment because a user will</a> <a data-t="2535">require to have to submit a ticket</a> <a data-t="2538">in order to get access to a package. But the issue</a> <a data-t="2541">is that the folks that are approving said tickets don't</a> <a data-t="2544">have much regard for reproducibility. And they can just either deny</a> <a data-t="2547">or just add packages willy nilly, which could also</a> <a data-t="2550">result in dependency conflicts.</a></p>

<p><a data-t="2553">And then we have a blocked environment, which is just a</a> <a data-t="2556">lose-lose situation for both sides of the coin.</a> <a data-t="2559">In a blocked environment, usually the Internet is cut off.</a> <a data-t="2562">There's no way to reach out externally for packages.</a> <a data-t="2565">And so in order to use functions outside</a> <a data-t="2568">of base R, users are going to have to figure out</a> <a data-t="2571">some backdoor ways to get packages in there and it causes security</a> <a data-t="2574">concerns. So this is never a good solution really</a> <a data-t="2577">for any team.</a></p>
